23  Appendix B — System Type Taxonomy v0.1

Architectural knowledge becomes significantly more useful when systems can be classified according to recognizable categories.

Without classification, blueprint repositories quickly become difficult to navigate. Engineers searching for architectural examples must manually inspect large numbers of unrelated systems, reducing the efficiency of blueprint retrieval and reuse.

This appendix presents System Type Taxonomy v0.1, a comprehensive classification system for common software system categories. The taxonomy provides a consistent way to label blueprints according to the primary type of system they represent.

This appendix includes: - The complete taxonomy with 7 core system types - Detailed characteristics and patterns for each type - Typical complexity ranges and common technologies - Classification decision guidelines - Hybrid system handling strategies - Examples and cross-references to Appendix D

23.1 Taxonomy Design Principles

The classification system follows several guiding principles that ensure stability and usefulness across technological changes.

23.1.1 1. Architectural Purpose Over Implementation

System types are defined according to their primary architectural purpose, not the technologies used to implement them.

Example: Both a Python Flask application and a Node.js Express application can be classified as “Web Applications” if they serve similar architectural purposes. The technology stack is implementation detail, not type-defining characteristic.

23.1.2 2. Architectural Behavior Focus

The taxonomy emphasizes architectural behavior—how systems process inputs, coordinate components, and manage data flows.

Example: Workflow Engines and Data Pipelines may both process sequences of operations, but they differ in architectural behavior—Workflow Engines coordinate and control, while Data Pipelines transform and transport.

23.1.3 3. Stability Across Technology Changes

The taxonomy aims to remain stable across technological changes. New programming languages and infrastructure tools appear frequently, but fundamental architectural categories evolve more slowly.

Example: The concept of “API” has remained stable despite shifts from REST to GraphQL to gRPC. Systems exposing programmable interfaces remain “APIs and Services” regardless of protocol evolution.

23.1.4 4. Practical Classification Clarity

The taxonomy balances comprehensiveness with practical clarity. Categories should be distinct enough to enable confident classification without excessive ambiguity.

Example: Rather than creating separate categories for “Microservices” and “Monoliths,” both are classified based on their architectural purpose (e.g., Web Application, API System). Deployment patterns are secondary characteristics.

23.2 Core System Types

The following system types form the initial classification set for Blueprint Taxonomy v0.1. Each type includes:

  • Definition: Core architectural purpose
  • Typical Components: Common structural elements
  • Key Characteristics: Distinguishing features
  • Complexity Range: Typical size/scale
  • Common Patterns: Recurring architectural approaches
  • Example Technologies: Representative implementations

23.2.1 1. CLI Tools

23.2.1.1 Definition

Command-line tools are systems designed to be executed through textual command interfaces. They typically process command-line arguments, perform operations, and output results to stdout or files.

23.2.1.2 Typical Components

  • Command Parser: Interprets command-line arguments and options
  • Task Executor: Performs the primary operations
  • Input/Output Handler: Manages stdin, stdout, stderr, and file I/O
  • Configuration Manager: Loads and manages configuration files
  • Error Handler: Manages error conditions and exit codes

23.2.1.3 Key Characteristics

  • Single execution context (no long-running processes)
  • Text-based input and output
  • Exit code-based success/failure signaling
  • Often focused on single-purpose operations
  • Minimal runtime state
  • Composable via pipes and shell scripting

23.2.1.4 Complexity Range

  • toy: Simple single-command utilities (e.g., hello, echo)
  • small: Multi-command tools with basic configuration (e.g., git, npm)
  • medium: Complex tools with plugins and extensibility (e.g., kubectl, docker)
  • large: Full-featured development environments (rare for CLI)

23.2.1.5 Common Patterns

  • Command Pattern: Each command is a separate handler
  • Flag-Based Configuration: Options and flags control behavior
  • Pipeline Integration: Designed for use in shell pipelines
  • Plugin Architecture: Extensible via plugins (e.g., VSCode CLI)

23.2.1.6 Example Technologies

  • Rust: clap, structopt for argument parsing
  • Go: cobra, urfave/cli for CLI frameworks
  • Python: argparse, click, typer
  • Node.js: commander, yargs

23.2.1.7 Classification Decision Tree

Is the system primarily executed via command line?
├─ Yes → Is it a long-running daemon/service?
│   ├─ Yes → May be "APIs and Services" or "Platform"
│   └─ No → CLI Tool ✓
└─ No → Consider other types

23.2.2 2. Web Applications

23.2.2.1 Definition

Web applications provide user-facing functionality through web interfaces. They typically combine frontend components, backend application services, and persistent storage systems.

23.2.2.2 Typical Components

  • Frontend Application: Browser-based user interface
  • API Layer: HTTP-based API for client-server communication
  • Application Services: Backend business logic
  • Authentication/Authorization: User identity and access control
  • Database: Persistent storage
  • Static Asset Server: Serves CSS, JavaScript, images
  • CDN: Content delivery for performance

23.2.2.3 Key Characteristics

  • HTTP-based client-server communication
  • Browser-based user interface
  • Session management and state persistence
  • Multi-user concurrent access
  • Responsive/adaptive UI design
  • SEO considerations for public-facing apps

23.2.2.4 Complexity Range

  • toy: Single-page static websites
  • small: Simple CRUD applications (e.g., blog, portfolio)
  • medium: Multi-user applications with collaboration features (e.g., project management)
  • large: Enterprise applications with complex workflows (e.g., ERP, CRM)

23.2.2.5 Common Patterns

  • Layered Architecture: Frontend → API → Service → Database
  • Single Page Application (SPA): React/Vue/Angular with REST/GraphQL API
  • Server-Side Rendering (SSR): Next.js, Nuxt.js for SEO and performance
  • Microfrontend: Multiple teams developing independent frontend modules
  • CQRS: Separate read and write models for complex domains

23.2.2.6 Example Technologies

  • Frontend: React, Vue, Angular, Svelte
  • Backend: Node.js (Express), Python (Django/FastAPI), Ruby (Rails), Java (Spring Boot)
  • API: REST, GraphQL, gRPC-Web
  • Database: PostgreSQL, MySQL, MongoDB, PostgreSQL

23.2.2.7 Classification Decision Tree

Does the system provide a browser-based user interface?
├─ Yes → Web Application ✓
└─ No → Consider other types

23.2.3 3. APIs and Services

23.2.3.1 Definition

API systems expose functionality through programmable interfaces that allow other systems to interact with them. They emphasize clearly defined interface contracts and service boundaries.

23.2.3.2 Typical Components

  • API Gateway: Request routing, authentication, rate limiting
  • Service Endpoints: Business logic exposed via API
  • Authentication Service: Token issuance and validation
  • Rate Limiting Engine: Protects against abuse
  • Documentation Generator: API specification and interactive docs
  • Monitoring/Logging: Request tracking and performance metrics

23.2.3.3 Key Characteristics

  • Programmatic interface (not UI-focused)
  • Well-defined API contracts (OpenAPI, gRPC, GraphQL schemas)
  • Service-oriented boundaries
  • Often stateless or limited state
  • Designed for integration by other systems
  • Emphasis on interface stability and versioning

23.2.3.4 Complexity Range

  • toy: Simple REST API with 1-2 endpoints
  • small: REST API with authentication and basic CRUD operations
  • medium: Comprehensive API with multiple services, caching, rate limiting
  • large: Complex service ecosystem with microservices, API mesh, multiple protocols

23.2.3.5 Common Patterns

  • REST API: Resource-based HTTP endpoints
  • GraphQL: Query language with flexible data fetching
  • gRPC: High-performance RPC with protocol buffers
  • Event-Driven API: Asynchronous communication via events
  • API Versioning: Versioning strategies (URL versioning, header versioning)

23.2.3.6 Example Technologies

  • Frameworks: Express.js, FastAPI, Spring Boot, ASP.NET Core
  • API Gateways: Kong, Apigee, AWS API Gateway
  • Documentation: Swagger/OpenAPI, GraphQL Playground
  • Protocols: HTTP/REST, WebSocket, gRPC, GraphQL

23.2.3.7 Classification Decision Tree

Does the system expose a programmable interface for other systems?
├─ Yes → Is it primarily UI-driven (Web App)?
│   ├─ Yes → Web Application
│   └─ No → APIs and Services ✓
└─ No → Consider other types

23.2.4 4. Workflow Engines

23.2.4.1 Definition

Workflow systems coordinate sequences of tasks across multiple components or services. They emphasize orchestration logic, state management, and control flow rather than direct data processing.

23.2.4.2 Typical Components

  • Orchestrator: Manages workflow execution and state
  • Task Scheduler: Schedules and executes tasks
  • State Store: Maintains workflow state and history
  • Task Registry: Available tasks and their definitions
  • Event Bus: Handles workflow events and triggers
  • Retry/Backoff Handler: Manages task failure recovery
  • Timeout Manager: Enforces time limits

23.2.4.3 Key Characteristics

  • Coordinated task execution across components
  • Stateful workflow tracking (running, completed, failed)
  • Conditional branching and parallel execution
  • Error handling and retry mechanisms
  • Long-running processes (hours to days)
  • Human-in-the-loop workflows (approvals, reviews)

23.2.4.4 Complexity Range

  • toy: Simple sequential task execution
  • small: Conditional workflows with basic error handling
  • medium: Complex workflows with parallel execution, retries, timeouts
  • large: Enterprise workflow systems with human workflows, SLA management

23.2.4.5 Common Patterns

  • Sequential Workflow: Tasks execute in order
  • Parallel Workflow: Multiple tasks execute simultaneously
  • Conditional Workflow: Branching based on conditions
  • Sub-Workflow: Nested workflow definitions
  • Saga Pattern: Compensating transactions for distributed workflows

23.2.4.6 Example Technologies

  • Workflow Engines: Apache Airflow, Prefect, Temporal, Camunda
  • Orchestration: Kubernetes Operators, Argo Workflows
  • Business Process: jBPM, Activiti, Camunda

23.2.4.7 Classification Decision Tree

Does the system primarily coordinate and sequence tasks across components?
├─ Yes → Workflow Engine ✓
└─ No → Consider other types

23.2.5 5. Data Pipelines

23.2.5.1 Definition

Data pipeline systems process and transform data across multiple stages. They typically include ingestion, transformation, and storage components for data movement and processing.

23.2.5.2 Typical Components

  • Ingestion Layer: Data collection from sources
  • Message Queue/Stream: Buffer for data movement
  • Transformation Engine: Data processing and enrichment
  • Validation/Quality Checks: Data quality enforcement
  • Storage Layer: Data persistence (data lake, warehouse)
  • Orchestration: Pipeline scheduling and dependency management
  • Monitoring: Pipeline health and data quality monitoring

23.2.5.3 Key Characteristics

  • Batch or streaming data processing
  • Data transformation and enrichment
  • Data quality validation
  • Schema evolution handling
  • Large-scale data volumes
  • Often time-series or event-based

23.2.5.4 Complexity Range

  • toy: Single transformation script
  • small: ETL pipeline with 2-3 stages
  • medium: Multi-source data integration with quality checks
  • large: Enterprise data platform with real-time streaming, ML integration

23.2.5.5 Common Patterns

  • Batch Processing: Scheduled ETL jobs (e.g., nightly)
  • Stream Processing: Real-time event processing (e.g., Kafka, Kinesis)
  • Lambda Architecture: Batch + stream processing layers
  • Delta Lake: ACID transactions on data lake storage
  • Change Data Capture (CDC): Track database changes in real-time

23.2.5.6 Example Technologies

  • Ingestion: Kafka, Kinesis, SQS, Pub/Sub
  • Processing: Apache Spark, Apache Flink, dbt, Pandas
  • Orchestration: Airflow, Dagster, Prefect
  • Storage: Snowflake, BigQuery, Redshift, Delta Lake, S3

23.2.5.7 Classification Decision Tree

Does the system primarily process, transform, and move data?
├─ Yes → Data Pipeline ✓
└─ No → Consider other types

23.2.6 6. Agent Systems

23.2.6.1 Definition

Agent systems consist of autonomous components capable of performing tasks, making decisions, and interacting with external environments. They emphasize planning, memory, and tool execution for complex task completion.

23.2.6.2 Typical Components

  • Planner: Determines action sequences to achieve goals
  • Execution Engine: Invokes tools and performs actions
  • Memory Store: Maintains context and history
  • Tool Adapter: Interfaces with external tools and APIs
  • Perception Module: Interprets environment and inputs
  • Decision Engine: Makes choices based on context and goals
  • Communication Protocol: Coordinates multiple agents

23.2.6.3 Key Characteristics

  • Autonomous decision-making
  • Goal-directed behavior
  • Stateful memory and context management
  • Tool use and external environment interaction
  • Iterative planning and execution cycles
  • Often multi-agent coordination

23.2.6.4 Complexity Range

  • toy: Simple single-tool agent
  • small: Agent with basic planning and tool use
  • medium: Multi-agent system with coordination and memory
  • large: Complex agent swarms with hierarchical organization

23.2.6.5 Common Patterns

  • ReAct Pattern: Reason + Act iteration loop
  • Tool Use: External API and function calling
  • Multi-Agent Coordination: Specialized agents collaborating
  • Memory Architectures: Short-term and long-term memory
  • Plan-and-Execute: Separate planning and execution phases

23.2.6.6 Example Technologies

  • Agent Frameworks: LangChain, AutoGPT, BabyAGI
  • Orchestration: LangGraph, Temporal (for agent workflows)
  • LLM Integration: OpenAI API, Anthropic API, local models

23.2.6.7 Classification Decision Tree

Does the system include autonomous components that make decisions and take actions?
├─ Yes → Agent System ✓
└─ No → Consider other types

23.2.7 7. Platforms

23.2.7.1 Definition

Platform systems provide infrastructure and services that support other applications. They emphasize extensibility, resource management, and service integration as foundational layers.

23.2.7.2 Typical Components

  • Resource Manager: Manages compute, storage, network resources
  • Service Catalog: Available services and capabilities
  • Tenant Management: Multi-tenancy and isolation
  • API Gateway: Platform-wide API routing
  • Authentication Service: Identity provider for platform users
  • Billing/Metering: Usage tracking and cost allocation
  • Developer Portal: Documentation and tools for platform users

23.2.7.3 Key Characteristics

  • Multi-tenant support
  • Self-service resource provisioning
  • Developer-focused user experience
  • Extensibility via plugins/add-ons
  • Service marketplace or catalog
  • Resource quotas and limits

23.2.7.4 Complexity Range

  • toy: Simple development environment
  • small: PaaS with basic service offerings
  • medium: Full-featured cloud platform with multiple services
  • large: Major cloud provider (AWS, GCP, Azure scale)

23.2.7.5 Common Patterns

  • Multi-Tenancy: Shared infrastructure with tenant isolation
  • Service Mesh: Inter-service communication and security
  • Plugin Architecture: Extensible platform via plugins
  • Marketplace: Third-party services available through platform
  • DevOps Integration: CI/CD, monitoring, logging built-in

23.2.7.6 Example Technologies

  • Cloud Platforms: AWS, Google Cloud, Azure
  • PaaS: Heroku, Render, Railway
  • Container Platforms: Kubernetes, OpenShift, Docker Swarm
  • Developer Platforms: Vercel, Netlify, Cloudflare Workers

23.2.7.7 Classification Decision Tree

Does the system provide infrastructure/services that other applications build upon?
├─ Yes → Platform ✓
└─ No → Consider other types

23.3 Classification Decision Framework

When classifying a system, follow this systematic approach:

23.3.1 Step 1: Identify Primary Purpose

What is the main architectural purpose of the system? Consider:

  • What problem does it solve?
  • Who are its primary consumers?
  • What is its primary mode of interaction?

23.3.2 Step 2: Apply Decision Trees

Use the decision trees provided for each system type to narrow down possibilities.

23.3.3 Step 3: Check Key Characteristics

Verify that the system matches the key characteristics of the candidate type:

  • Component structure
  • Communication patterns
  • State management
  • Interaction mode

23.3.4 Step 4: Handle Ambiguity

If multiple types seem applicable:

  1. Choose Primary Type: What is the dominant architectural pattern?
  2. Add Secondary Type Tags: Note secondary characteristics
  3. Document Hybrid Nature: Explain the hybrid composition

23.3.5 Step 5: Validate with Examples

Compare with example blueprints in Appendix D to validate the classification.

23.4 Hybrid Systems

In practice, many real-world systems combine characteristics from multiple categories. This section provides guidance for handling hybrid systems.

23.4.1 Common Hybrid Patterns

23.4.1.1 1. Web Platform

Composition: Web Application + Platform

Characteristics: - Web application interface for users - Platform services for developers/customers - API layer supporting both UI and third-party integrations

Classification: Primary type based on dominant purpose, with secondary tag

Example: GitHub (Web Application for code hosting, Platform for developer tools)

23.4.1.2 2. API-First Web Application

Composition: Web Application + API System

Characteristics: - Well-defined API used by both web frontend and external consumers - API design drives architecture, not an afterthought - Often serves mobile clients alongside web UI

Classification: Web Application (if UI is primary) or API System (if API is primary)

Example: Stripe (API-first with web dashboard as secondary interface)

23.4.1.3 3. Data-Driven Web Application

Composition: Web Application + Data Pipeline

Characteristics: - Web application for user interaction - Internal data pipelines for analytics and reporting - Real-time dashboards and data visualization

Classification: Web Application with internal Data Pipeline components

Example: Analytics dashboard platforms (Mixpanel, Amplitude)

23.4.1.4 4. Orchestration Platform

Composition: Platform + Workflow Engine

Characteristics: - Platform infrastructure for resource management - Workflow engine capabilities for task coordination - User workflows managed on top of platform resources

Classification: Platform with integrated Workflow Engine

Example: Kubernetes (Platform for container orchestration with workflow capabilities)

23.4.2 Hybrid System Documentation

When documenting a hybrid system:

blueprint:
  id: com.example.hybrid.v1
  system_type: Web Application  # Primary type
  complexity: large
  tags:
    - platform  # Secondary characteristic
    - data_pipeline  # Secondary characteristic

  # ... rest of blueprint

Include additional context in the Markdown body:

# System Classification

This system is classified as a **Web Application** (primary type) with **Platform** and **Data Pipeline** characteristics:

1. **Web Application**: Primary user interface is browser-based for task management
2. **Platform**: Exposes APIs and services for third-party integrations and extensions
3. **Data Pipeline**: Internal ETL processes for analytics and reporting

The architecture combines elements from all three system types while maintaining a cohesive user experience.

23.5 Complexity Classification

Each system type should be classified by complexity to guide blueprint detail level and architectural expectations.

23.5.1 Complexity Definitions

Complexity Scale Team Size Typical Users Blueprint Detail
toy Proof-of-concept 1 person Developer testing Minimal, focus on structure
small Production system 1-3 people Single team Complete with key workflows
medium Multi-team system 3-10 people Multiple teams Comprehensive with all details
large Enterprise system 10+ people Organization-wide Exhaustive with edge cases

23.5.2 Complexity Indicators

Consider these factors when determining complexity:

Component Count: - toy: 1-3 components - small: 3-10 components - medium: 10-30 components - large: 30+ components

Interface Count: - toy: 1-3 interfaces - small: 3-10 interfaces - medium: 10-30 interfaces - large: 30+ interfaces

Workflow Complexity: - toy: 1-2 simple workflows - small: 3-5 workflows with some branching - medium: 5-15 workflows with error handling - large: 15+ workflows with complex orchestration

Team Requirements: - toy: Single developer can build and maintain - small: Small team, limited specialization - medium: Multiple teams with clear boundaries - large: Multiple teams with extensive coordination

23.5.3 Complexity Adjustment

If a system spans multiple dimensions (e.g., many components but simple workflows), use the dominant dimension to determine complexity.

Example: A data pipeline with 20 components but only 2 sequential stages might be classified as medium rather than large because workflow complexity is low.

23.6 Taxonomy Usage Guidelines

23.6.1 For Blueprint Authors

  1. Choose Primary Type: Select the single best match for architectural purpose
  2. Add Tags: Use tags for secondary characteristics
  3. Document Hybrid Nature: Explain if combining multiple types
  4. Reference Examples: Check Appendix D for similar system types

23.6.2 For Blueprint Consumers

  1. Search by Type: Use system type to find relevant blueprints
  2. Filter by Complexity: Narrow to appropriate scale
  3. Study Patterns: Understand common patterns for the type
  4. Adapt Appropriately: Adapt patterns to specific context

23.6.3 For Blueprint Curators

  1. Validate Classifications: Ensure consistent application of taxonomy
  2. Tag Hybrids: Identify systems with multiple type characteristics
  3. Maintain Examples: Keep representative examples for each type
  4. Evolve Taxonomy: Review and refine as new patterns emerge

23.8 Taxonomy Evolution Roadmap

This taxonomy is v0.1 and will evolve based on:

  1. Blueprint Repository Growth: New patterns emerging from practice
  2. Technology Shifts: New architectural paradigms (e.g., serverless, edge computing)
  3. Community Feedback: Classification challenges and edge cases
  4. Research Findings: Architectural research and pattern discovery

23.8.1 Planned Revisions

v0.2 (Expected): - Add “Serverless Functions” as distinct type or subcategory - Refine “Agent Systems” based on emerging patterns - Add complexity indicators for each type

v1.0 (Expected): - Stable taxonomy with comprehensive type coverage - Formal classification schema - Automated classification heuristics

23.8.2 Contribution Guidelines

When proposing taxonomy changes:

  1. Document Need: Explain why current taxonomy is insufficient
  2. Provide Examples: Show real-world systems that need new classification
  3. Propose Structure: Define new type with characteristics and patterns
  4. Validate: Test against existing blueprints

23.9 Summary

The System Type Taxonomy v0.1 provides:

✓ 7 Core System Types: CLI Tools, Web Applications, APIs and Services, Workflow Engines, Data Pipelines, Agent Systems, Platforms

✓ Clear Classification Guidelines: Decision trees and characteristics for confident classification

✓ Hybrid System Support: Framework for documenting multi-type systems

✓ Complexity Classification: Scale indicators to guide blueprint detail

✓ Practical Utility: Searchable, retrievable, and comparable system architectures

By using this taxonomy consistently, teams can:

  • Organize blueprint repositories effectively
  • Find relevant architectural examples quickly
  • Identify patterns across similar systems
  • Enable automated analysis and composition
  • Build a shared architectural vocabulary

This foundation supports the broader goals of blueprint-based system engineering: reusable, composable, and computable architectural knowledge.
