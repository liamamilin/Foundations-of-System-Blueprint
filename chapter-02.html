5  What People Think They Have vs What They Actually Have

Most engineering teams believe they already possess the artifacts required to understand and maintain their systems.

A typical project contains a variety of documents and resources:

  • README files

  • design documents

  • architecture diagrams

  • API documentation

  • ADRs (Architecture Decision Records)

  • source code repositories

At first glance, this collection appears sufficient. The system seems documented, decisions seem recorded, and the implementation is fully available in code.

However, a closer examination reveals a crucial discrepancy.

What teams believe they possess is system knowledge.
What they actually possess is a collection of disconnected information artifacts.

The difference between these two is fundamental. Information fragments can describe parts of a system, but they do not necessarily reveal the structure of the system itself.

Understanding this distinction requires examining the limitations of the artifacts most commonly used in software engineering.

5.1 The Limits of README, Documentation, ADR, and Design Documents

Engineering documentation serves many useful purposes. It explains how to run a system, describes design decisions, and records operational procedures.

However, each type of document captures only a specific aspect of the system, rather than the system as a whole.

README files typically describe project setup, usage instructions, and development workflows. They are useful entry points but rarely contain architectural structure.

Design documents often describe the rationale behind a specific feature or subsystem. While they may include diagrams and technical explanations, they usually focus on a single change rather than the system’s overall architecture.

Architecture Decision Records capture the reasoning behind particular technical choices. They provide historical context but do not provide a structural representation of the system itself.

Operational documentation describes deployment procedures, monitoring strategies, and maintenance tasks. These documents explain how the system is operated rather than how it is structured.

Each artifact therefore addresses a different concern. Taken together, they form a fragmented view of the system.

None of them provides a single structural model that explains how all parts of the system relate to each other.

5.2 Code Represents Facts, but Facts Are Not Explanations

Source code is often considered the ultimate documentation of a system. In many engineering cultures, developers repeat a common phrase: “the code is the source of truth.”

This statement is partially correct.

Code does contain the most accurate description of how the system behaves at runtime. It specifies algorithms, data transformations, control flows, and interactions between modules.

However, code primarily records facts, not explanations.

A codebase can reveal what the system does, but it rarely explains why the system was designed in a particular way. It does not clearly express the architectural intentions behind component boundaries, communication protocols, or data ownership rules.

To reconstruct this reasoning, engineers must analyze the implementation and infer the original design decisions.

This process is expensive and error-prone. Different engineers may interpret the same code in different ways, leading to inconsistent mental models of the system.

In other words, code provides behavioral precision, but it does not provide architectural clarity.

5.3 Why More Documentation Often Creates More Confusion

When teams recognize that understanding is deteriorating, the typical response is to produce additional documentation.

New diagrams are created. Additional design documents are written. Internal knowledge bases expand.

Paradoxically, this often makes the situation worse.

Without a consistent structural model, new documents simply add more fragments to the existing collection. Each artifact describes the system from a different perspective, using different terminology and levels of abstraction.

Over time, inconsistencies accumulate.

Two documents may describe the same subsystem differently. Architecture diagrams may diverge from the actual code. Historical documents may describe designs that are no longer valid.

As the volume of documentation increases, the effort required to determine which artifacts are accurate also increases.

Eventually, engineers lose trust in the documentation entirely.

At that point, documentation ceases to function as a reliable source of knowledge.

5.4 The Critical Distinction: Information vs Structure

The underlying issue can be understood through a simple distinction.

Engineering artifacts typically provide information.
What engineers actually need is structure.

Information describes individual elements of a system:

  • configuration details

  • interface descriptions

  • operational instructions

  • implementation logic

Structure describes the relationships between those elements.

It explains how components interact, how data flows across boundaries, how responsibilities are distributed, and how constraints shape the behavior of the system.

Information answers questions such as:

What command starts the service?
What parameters does this API accept?
What configuration file controls this feature?

Structure answers different questions:

Which component owns this data?
How do requests propagate across services?
Where are the architectural boundaries of the system?
What constraints govern system evolution?

Information can accumulate indefinitely.
Structure must remain coherent.

Without structure, information becomes noise.

5.5 The Three Consequences of Missing Structure

When structural knowledge is absent, software systems experience three recurring difficulties.

The first is understanding.

Engineers cannot easily determine how the system is organized. Investigating a single feature may require exploring multiple repositories, documents, and runtime behaviors. Even experienced developers must rely on partial mental models.

The second is collaboration.

Different teams interpret the architecture differently. Without a shared structural model, coordination becomes difficult. Changes made by one team may conflict with assumptions held by another.

The third is evolution.

Systems evolve over time as new features are added and technologies change. Without a stable structural representation, modifications often introduce unintended consequences. Refactoring becomes risky because the architectural dependencies are unclear.

These three problems—understanding, collaboration, and evolution—are often treated as separate challenges. In reality, they share the same root cause.

The system lacks a structured representation of its architecture.
