5  What People Think They Have vs What They Actually Have

Most engineering teams believe they already possess the artifacts and resources required to understand and maintain their systems effectively.

A typical software project contains a diverse collection of documentation and structural resources:

  • README files explaining setup and usage

  • Design documents describing specific features or subsystems

  • Architecture diagrams illustrating component relationships

  • API documentation specifying interfaces and contracts

  • Architecture Decision Records (ADRs) capturing design rationale

  • Source code repositories containing implementation details

  • Operational procedures and runbooks for deployment and maintenance

At first glance, this comprehensive collection appears sufficient. The system seems thoroughly documented, decisions appear recorded, and the implementation is fully available in the codebase.

However, a closer examination reveals a crucial and fundamental discrepancy.

What teams believe they possess is system architectural knowledge—a coherent, comprehensive understanding of the system’s structure and behavior. What they actually possess is a collection of disconnected information artifacts that describe fragments of the system from different perspectives, using different terminology, at different levels of abstraction, with no unified structural framework.

The difference between these two is profound and consequential. Information fragments can describe parts of a system in isolation, but they do not necessarily reveal the structural relationships, interaction patterns, and architectural coherence that define the system as a whole.

Understanding this distinction requires examining the limitations of the artifacts most commonly used in software engineering and recognizing why they are insufficient for representing complete system architectural knowledge.

5.1 The Limits of README, Documentation, ADR, and Design Documents

Engineering documentation serves many valuable and necessary purposes. It explains how to run a system, describes design decisions and their rationale, records operational procedures, and facilitates communication between team members.

However, each type of document captures only a specific, limited aspect of the system rather than representing the system as a coherent architectural whole.

README files typically describe project setup, installation procedures, usage instructions, and development workflows. They serve as useful entry points for new team members but rarely contain architectural structure beyond basic component lists or dependency descriptions.

Design documents often describe the rationale behind a specific feature, subsystem, or architectural change. While they may include diagrams and technical explanations, they usually focus on a single change or subsystem rather than the system’s overall architectural structure and coherence.

Architecture Decision Records capture the reasoning behind particular technical choices, such as technology selection, system decomposition strategies, or interface design patterns. They provide valuable historical context for understanding why specific decisions were made, but they do not provide a structural representation of the system itself or how components relate to each other.

Operational documentation describes deployment procedures, monitoring strategies, maintenance tasks, and troubleshooting processes. These documents explain how the system is operated and maintained in production environments rather than how it is structured architecturally.

Each artifact therefore addresses a different concern and serves a specific purpose. Taken together, they form a fragmented, piecemeal view of the system—like having several photographs of different parts of a building without a floor plan showing how those parts connect and relate.

None of these artifacts provides a single, coherent structural model that explains how all parts of the system relate to each other, how components interact through defined interfaces, how data flows across boundaries, and how the system as a whole achieves its goals.

5.2 Code Represents Facts, but Facts Are Not Explanations

Source code is often considered the ultimate documentation of a system—the “source of truth” that definitively describes what the system does. In many engineering cultures, developers repeat a common aphorism: “the code is the documentation.”

This statement contains an important element of truth.

Code does contain the most accurate and precise description of how the system behaves at runtime. It specifies algorithms, data transformations, control flows, state management, and interactions between modules with unambiguous detail.

However, code primarily records implementation facts—what the system does—rather than architectural explanations—why the system was designed that way and what structural principles govern its organization.

A codebase can reveal what the system does in precise detail, but it rarely explains the architectural rationale behind component boundaries, communication patterns, data ownership rules, or operational constraints. These architectural decisions are often implicit in the code structure rather than explicitly documented or explained.

To reconstruct this architectural reasoning, engineers must analyze the implementation and infer the original design decisions, component responsibilities, and architectural patterns that guided the system’s structure.

This process is expensive, time-consuming, and error-prone. Different engineers may interpret the same code in different ways, leading to inconsistent mental models of the system’s architecture and conflicting interpretations of design intent.

In other words, code provides behavioral precision at the implementation level, but it does not provide architectural clarity at the structural level.

Code describes the implementation, but not the architecture that guided that implementation.

5.3 Why More Documentation Often Creates More Confusion

When teams recognize that system understanding is deteriorating—that new engineers struggle to understand the system, changes become increasingly risky, and architectural coherence begins to erode—the typical response is to produce additional documentation.

New architecture diagrams are created to capture system structure. Additional design documents are written to explain subsystems and features. Internal knowledge bases and wikis expand with more descriptions and explanations.

Paradoxically, this often makes the situation worse rather than better.

Without a consistent structural model or shared framework for organizing system knowledge, new documents simply add more fragments to the existing collection of disconnected artifacts. Each artifact describes the system from a different perspective, using different terminology, at different levels of abstraction, and potentially based on outdated or incomplete understanding.

Over time, inconsistencies accumulate as the system evolves and documentation is updated inconsistently or not at all.

Two documents may describe the same subsystem differently, using different component names or architectural models. Architecture diagrams may diverge from the actual codebase as components are added or modified. Historical documents may describe designs that are no longer valid or have been superseded by new architectures.

As the volume of documentation increases, the effort required to determine which artifacts are accurate, current, and authoritative also increases. Engineers must navigate through multiple conflicting descriptions, uncertain which version represents the current reality of the system.

Eventually, engineers lose trust in the documentation entirely, preferring to rely on code inspection, informal conversations, or personal experience rather than consulting potentially outdated or conflicting documentation.

At that point, documentation ceases to function as a reliable source of architectural knowledge and becomes instead a source of confusion and misinformation.

5.4 The Critical Distinction: Information vs Structure

The underlying issue can be understood through a fundamental distinction that applies to all forms of knowledge representation.

Engineering artifacts typically provide information about a system. What engineers actually need for effective system understanding and evolution is structure—the coherent framework that organizes and relates that information.

Information describes individual elements of a system in isolation:

  • Configuration details and parameter settings

  • Interface specifications and API contracts

  • Operational instructions and procedures

  • Implementation logic and algorithms

Structure describes the relationships between those elements—the framework that explains how elements connect, interact, and combine to form a coherent system.

Structure explains how components interact and depend on each other, how data flows across system boundaries and between components, how responsibilities are distributed across the architecture, and how constraints shape and govern system behavior and evolution.

Information answers questions such as:

  • What command starts the service?

  • What parameters does this API accept?

  • What configuration file controls this feature?

  • How do I deploy this system to production?

Structure answers fundamentally different questions:

  • Which component owns this data and is responsible for its consistency?

  • How do requests propagate across services and what are the communication patterns?

  • Where are the architectural boundaries of the system and what defines them?

  • What constraints govern system evolution and what architectural principles must be preserved?

Information can accumulate indefinitely without becoming problematic in itself—it is simply data about the system. Structure must remain coherent and consistent—fragmented or contradictory structure leads directly to confusion and misunderstanding.

Without structure, information becomes noise—data without framework, details without context, facts without meaning.

5.5 The Three Consequences of Missing Structure

When structural architectural knowledge is absent or inadequately represented, software systems experience three recurring and interconnected difficulties that undermine engineering effectiveness.

The first difficulty is understanding—the ability to comprehend the system’s architecture as a coherent whole.

Engineers cannot easily determine how the system is organized at a structural level. Investigating a single feature or capability may require exploring multiple code repositories, scattered documents, and runtime behaviors to piece together an incomplete understanding. Even experienced developers must rely on partial mental models that may differ from person to person, leading to inconsistent interpretations and decisions.

The second difficulty is collaboration—the ability for multiple teams to work together effectively on the same system.

Different teams interpret the architecture differently based on their local perspectives and limited visibility. Without a shared structural model that provides a coherent view of the entire system, coordination becomes difficult and error-prone. Changes made by one team may conflict with assumptions held by another team, leading to integration problems, unexpected side effects, and architectural degradation over time.

The third difficulty is evolution—the ability to modify and extend the system safely and effectively.

Systems evolve over time as new features are added, technologies change, and requirements shift. Without a stable, explicit structural representation, modifications often introduce unintended consequences and unexpected interactions. Refactoring becomes risky because the architectural dependencies and impact boundaries are unclear. Engineers cannot reliably predict how a change will affect other parts of the system without extensive testing and analysis.

These three problems—understanding, collaboration, and evolution—are often treated as separate, independent challenges that require different solutions. In reality, they share the same root cause.

The system lacks a structured, explicit representation of its architecture—a blueprint that provides the coherent structural framework necessary for effective system understanding, collaboration, and evolution.
