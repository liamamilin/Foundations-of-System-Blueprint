10  System Knowledge Artifacts (A Taxonomy)

Software engineering relies on a wide range of artifacts to represent system knowledge.

Over the years, different communities have introduced their own formats for describing systems, documenting decisions, and communicating architectural ideas. These artifacts include requirements documents, architectural diagrams, decision records, interface specifications, and operational guides.

Each artifact plays a useful role within the engineering process. However, these artifacts were not designed as parts of a unified system knowledge model. Instead, they evolved independently to address specific communication needs.

As a result, modern software projects accumulate many artifacts, but those artifacts rarely form a coherent structure.

This chapter introduces a taxonomy of system knowledge artifacts and explains why existing artifacts alone cannot support systematic architecture reuse. It also establishes the role of the blueprint as the central model that organizes these artifacts into a consistent framework.

10.1 Common Artifacts in Engineering Practice

Most software projects produce a diverse set of documentation and structural descriptions. Some artifacts originate from product management, while others are produced by architects, developers, or operations teams.

Understanding these artifacts is the first step toward organizing them into a coherent system knowledge model.

10.1.1 Product Requirement Documents (PRD)

Product Requirement Documents describe user needs, product goals, and feature requirements.

PRDs typically include:

  • Problem statements and user pain points
  • Functional requirements and feature descriptions
  • User personas and use cases
  • Success metrics and acceptance criteria

PRDs serve as the primary artifact for capturing intent. They describe what a system should accomplish but do not specify how it should be structured.

10.1.2 Architecture Decision Records (ADR)

Architecture Decision Records capture the reasoning behind particular technical decisions, such as technology selection or system decomposition strategies.

ADRs typically include:

  • The context and problem being addressed
  • The decision that was made
  • The consequences and trade-offs of the decision
  • Alternatives that were considered

ADRs serve as historical records of architectural reasoning. They preserve the why behind structural choices, helping future engineers understand the rationale behind current designs.

10.1.3 Requests for Comments (RFC)

Requests for Comments are proposals used to introduce and discuss architectural changes before they are implemented.

RFCs typically include:

  • Motivation for the proposed change
  • Technical details of the proposed design
  • Impact analysis and risk assessment
  • Discussion and feedback from stakeholders

RFCs facilitate collaborative decision-making by allowing teams to review and refine architectural proposals before implementation begins.

10.1.4 Unified Modeling Language (UML) Diagrams

UML diagrams represent structural or behavioral aspects of a system using standardized graphical notation.

Common UML diagram types include:

  • Class diagrams: Show static structure and relationships
  • Sequence diagrams: Show interaction sequences
  • Component diagrams: Show system components and their connections
  • Deployment diagrams: Show physical deployment structures

UML diagrams provide visual representations of system structure, making architectural relationships easier to understand. However, they often operate as standalone artifacts rather than being integrated into a broader knowledge model.

10.1.5 API Specifications

API specifications define external interfaces and communication protocols between services.

API specifications typically include:

  • Endpoint definitions and methods
  • Request and response schemas
  • Authentication and authorization requirements
  • Error handling and status codes

API specifications serve as contracts between services, defining how components should interact. They are critical for integration but typically describe only the interface layer of a system.

10.1.6 Operational Runbooks

Operational runbooks describe the procedures required to deploy, maintain, and troubleshoot systems in production environments.

Runbooks typically include:

  • Deployment procedures and configurations
  • Monitoring and alerting setup
  • Troubleshooting guides and diagnostic procedures
  • Disaster recovery and failover procedures

Operational runbooks capture the operational layer of system knowledge, focusing on runtime behavior rather than structural design.

10.1.7 Summary of Common Artifacts

Artifact Primary Focus Typical Audience Layer
PRD Goals and capabilities Product managers, stakeholders Intent
ADR Architectural reasoning Architects, engineers Blueprint
RFC Proposed changes All stakeholders Blueprint
UML Diagrams Visual structure Architects, engineers Blueprint
API Specifications Interface contracts Developers, integrators Blueprint
Runbooks Operational procedures Operations teams Blueprint

Each of these artifacts contributes valuable information about the system. However, they are typically created independently, using different formats, assumptions, and conceptual models.

Consequently, they describe different slices of system knowledge, rather than a unified architectural structure.

10.2 Why These Artifacts Cannot Be Automatically Combined

Although the artifacts listed above contain useful information, they are difficult to combine into a coherent system model.

The fundamental reason is the absence of a shared ontology.

The Ontology Problem

An ontology defines the set of concepts and relationships used to describe a domain. It provides a common vocabulary and structure that allows different artifacts to refer to the same concepts consistently.

Without a shared ontology, different artifacts may refer to similar ideas using different terminology or levels of abstraction.

Example: The Order Processing Capability

Consider how different artifacts might describe the same capability:

  • A PRD may describe a capability called “order processing” with requirements for creating, updating, and canceling customer orders
  • An architecture diagram may represent this capability as a “Order Service” component with interfaces to a “Payment Service” and “Inventory Service”
  • A codebase may implement this capability as a collection of classes: OrderController, OrderRepository, OrderValidator, and OrderEventHandler
  • An API specification may define endpoints like POST /orders, PUT /orders/{id}, and DELETE /orders/{id}
  • An operational runbook may describe procedures for monitoring order throughput, retrying failed orders, and scaling the Order Service

Each artifact refers to the same conceptual element—the order processing capability—but uses different names, representations, and levels of detail.

The Manual Mapping Problem

Without a shared ontology, integrating information across artifacts requires manual interpretation. Engineers must:

  • Recognize that “order processing” in the PRD, “Order Service” in the diagram, and the OrderController class in code all refer to the same capability
  • Map relationships between requirements, components, and implementation elements
  • Reconstruct the complete architectural picture from fragmentary sources

This manual mapping process is:

  • Time-consuming: Engineers must spend significant effort understanding how different artifacts relate
  • Error-prone: Misinterpretations can lead to incorrect assumptions about system structure
  • Non-scalable: As systems grow, the number of artifacts and their relationships becomes overwhelming
  • Fragile: Knowledge is lost when engineers leave the organization, requiring reconstruction from scratch

The Structural Inconsistency Problem

Even when artifacts describe the same concepts, they may represent them using incompatible structures:

  • A PRD may organize capabilities by user value (e.g., “checkout experience”)
  • An architecture diagram may organize components by technical boundaries (e.g., “backend services”)
  • Code may organize classes by implementation patterns (e.g., “controllers,” “repositories,” “models”)

These different organizational structures create impedance mismatches that make automated analysis or combination nearly impossible.

The Consequence: Isolated Knowledge Fragments

Without a shared ontology, artifacts remain isolated fragments of knowledge rather than components of an integrated system model.

Each fragment is valuable individually, but their collective value is limited because:

  • Engineers cannot easily find relevant information across artifacts
  • Automated tools cannot analyze relationships between artifacts
  • Changes in one artifact may not be reflected in related artifacts
  • Knowledge cannot be reused or composed across projects

The blueprint framework addresses this fragmentation by introducing a central structural model and a shared ontology for representing system knowledge.

10.3 Blueprint as the Parent Structure

The blueprint framework addresses the fragmentation problem by introducing a central structural model.

In this model, the blueprint functions as the parent structure that organizes system knowledge.

The Parent-Child Relationship

Instead of treating PRDs, ADRs, architecture diagrams, and specifications as independent artifacts, the blueprint framework interprets them as projections derived from the same underlying system model.

The blueprint captures the core structural representation of the system:

  • Components and their responsibilities
  • Interfaces and communication protocols
  • Data models and transformation rules
  • Workflows and operational sequences
  • Constraints and feasibility requirements

Other artifacts then become specialized views that emphasize particular aspects of this structure.

How the Blueprint Unifies Artifacts

Consider how the blueprint relates to the common artifacts:

Artifact Relationship to Blueprint
PRD Emphasizes the goal and capabilities elements of the blueprint
ADR Captures the reasoning behind blueprint decisions
RFC Proposes changes to the blueprint structure
UML Diagram Provides a visual projection of the blueprint’s components and interfaces
API Specification Emphasizes the interface elements of the blueprint
Runbook Emphasizes the workflow and operational constraints elements of the blueprint

Example: Unified Representation

Using the blueprint as the parent structure, the order processing capability would be represented consistently across all artifacts:

  • Blueprint: Defines the OrderProcessing component with clear responsibilities, interfaces to Payment and Inventory services, data models for orders, and workflows for order lifecycle management
  • PRD: References the blueprint’s goal and capabilities, describing order processing in terms of user value
  • Architecture Diagram: Visually projects the blueprint’s components and interfaces
  • API Specification: Projects the blueprint’s interface definitions as endpoint contracts
  • Runbook: Projects the blueprint’s workflows as operational procedures
  • Code: Implements the blueprint’s components and interfaces

All artifacts now reference the same underlying conceptual structure, using consistent terminology and relationships.

The Transformation From Fragments to Model

This perspective transforms the role of documentation:

  • Before: Artifacts are isolated fragments, each describing a different slice of the system
  • After: Artifacts are projections of a unified model, each emphasizing a different aspect of the same structure

This transformation has profound implications for system knowledge management:

  • Consistency: All artifacts remain consistent because they derive from the same blueprint
  • Comprehensibility: Engineers can navigate between artifacts using the blueprint as a map
  • Maintainability: Changes to the blueprint automatically update all related projections
  • Composability: Blueprint structures can be reused and composed across projects

10.4 Transformations Between Artifacts

Once artifacts are interpreted as projections of a blueprint, relationships between them become easier to understand.

Blueprint → Projections

A blueprint can generate multiple projections, each tailored to a specific audience or purpose.

For example, a blueprint describing a service-based system may produce:

  • an architecture projection showing service boundaries and dependencies
  • a specification projection describing interface contracts and acceptance criteria
  • an operational projection describing runtime workflows and monitoring points
  • a data projection describing data models and ownership boundaries

These projections are not independent documents—they are views extracted from the blueprint.

Projections → Blueprint

Conversely, existing artifacts can also serve as inputs for reconstructing a blueprint.

For instance:

  • Architectural diagrams may provide information about component structure and relationships
  • API specifications may provide interface definitions and communication protocols
  • Operational runbooks may provide workflow descriptions and operational constraints
  • PRDs may provide goals and capability definitions

By integrating information from these sources, engineers can reconstruct or populate a blueprint that captures the complete system architecture.

Bidirectional Transformation

The relationship between blueprints and projections is bidirectional:

  1. Blueprint → Projections: Generate specialized views from the central model
  2. Projections → Blueprint: Integrate information from multiple artifacts into a unified model

This bidirectional capability is significant because it enables automation.

Automated Transformations

If artifacts share a common structural foundation, tools can:

  • Generate projections automatically from blueprints, ensuring that all views remain synchronized
  • Extract blueprint elements from existing artifacts, accelerating the process of creating blueprints for legacy systems
  • Detect inconsistencies between projections, identifying cases where artifacts have diverged
  • Update related artifacts when the blueprint changes, maintaining consistency across the entire documentation set

Such capabilities are difficult to achieve when artifacts exist only as informal documents.

Example: Automated Consistency Checking

Consider a system where an architect modifies the blueprint to split a monolithic service into two separate services:

  • The blueprint is updated to reflect the new component structure
  • An automated tool generates an updated architecture projection showing the new service boundaries
  • Another tool detects that the API specification still describes endpoints that have been moved between services
  • A notification alerts the team to update the API specification to match the new blueprint

Without the blueprint as the parent structure, detecting this inconsistency would require manual review. With the blueprint model, consistency becomes automatable.

10.5 The Artifact Taxonomy

Based on the analysis in this chapter, we can establish a clear taxonomy of system knowledge artifacts.

Primary Artifacts

Artifact Role Relationship to Blueprint
Blueprint Central structural model The parent structure
Intent Goals and requirements Input to blueprint creation
Implementation Code and infrastructure Realization of blueprint

Derived Artifacts (Projections)

Artifact Projection Type Emphasized Blueprint Elements
Architecture Diagram Architecture Projection Components, interfaces, dependencies
API Specification Interface Projection Interface definitions, protocols
Specification Document Specification Projection Capabilities, acceptance criteria
Operational Runbook Operational Projection Workflows, operational constraints
Data Schema Data Projection Data models, ownership
Deployment Manifest Deployment Projection Component deployment, infrastructure

Supporting Artifacts

Artifact Role Relationship to Blueprint
ADR Historical reasoning Records decisions affecting blueprint
RFC Change proposals Proposed modifications to blueprint
Test Plans Verification Validate blueprint through implementation
Monitoring Dashboards Runtime observation Observe blueprint in operation

Key Insights from the Taxonomy

  1. Blueprints are primary: The blueprint is the central model from which other artifacts derive
  2. Projections are derived: Most documentation artifacts are projections rather than independent descriptions
  3. Supporting artifacts are contextual: ADRs, RFCs, and similar documents provide context and reasoning but do not define structure
  4. Implementation is realization: Code and infrastructure are the operational realization of the blueprint, not alternative descriptions

10.6 The Shift to Artifact Integration

The taxonomy introduced in this chapter leads to a fundamental shift in how engineering teams should think about system knowledge artifacts.

From: Fragmented Artifact Collection

  • Each artifact is created independently
  • Different formats, terminology, and conceptual models
  • Manual effort required to integrate information
  • Inconsistencies accumulate over time
  • Knowledge is difficult to reuse or compose

To: Unified Blueprint-Based Model

  • Blueprint serves as the central structural model
  • All artifacts are projections of or inputs to the blueprint
  • Consistent terminology and conceptual framework
  • Automated consistency checking and updates
  • Knowledge is reusable and composable

Practical Implications

This shift has several practical implications for engineering teams:

  1. Blueprint-First Approach: Create blueprints before or alongside other artifacts, establishing the central structural model
  2. Projections as Views: Treat architecture diagrams, specifications, and runbooks as views derived from the blueprint
  3. Artifact Synchronization: Use tools to ensure that projections remain synchronized with the blueprint
  4. Legacy Migration: Gradually migrate existing artifacts into a blueprint-based model by extracting structural information and consolidating it into blueprints
  5. Knowledge Accumulation: Store blueprints in repositories where they can be retrieved, reused, and composed across projects

10.7 Blueprint as the Primary Model

The taxonomy introduced in this chapter leads to a clear conclusion.

Among the many artifacts used in software engineering, only one artifact serves as the primary representation of system structure.

That artifact is the blueprint.

All other artifacts—requirements documents, architecture diagrams, decision records, and operational guides—can be interpreted as projections derived from the blueprint.

Why This Matters

By placing the blueprint at the center of the system knowledge model, the framework provides a consistent foundation for organizing architectural information.

This shift has important consequences:

1. From Independent Documents to Coherent Model

  • Before: Teams maintain independent documents for different purposes
  • After: Teams maintain a single blueprint model and generate specialized views when necessary

2. From Fragmented Knowledge to Integrated Understanding

  • Before: System architecture must be reconstructed from scattered artifacts
  • After: System architecture is directly accessible from the blueprint

3. From Ephemeral Documentation to Durable Knowledge

  • Before: Documentation becomes outdated and is often ignored
  • After: Blueprints are versioned, maintained, and treated as engineering assets

4. From Manual Integration to Automated Operations

  • Before: Integrating information across artifacts requires manual effort
  • After: Automated tools can analyze, transform, and validate artifacts based on the blueprint model

The Long-Term Vision

The blueprint model is not merely a documentation technique. It is the foundation for a new approach to system engineering:

  • Architecture Libraries: Collections of reusable blueprints that capture proven architectural patterns
  • Automated Reasoning: Tools that can analyze blueprints to detect inconsistencies, suggest improvements, or validate designs
  • System Composition: Methods for combining blueprints into larger architectures through automated composition rules
  • Architecture Intelligence: AI systems that can learn from blueprint repositories and assist in architectural design

These capabilities depend on having blueprints as the primary model for representing system structure.

10.8 Summary

This chapter has established a taxonomy of system knowledge artifacts and clarified the role of the blueprint within that taxonomy:

Key Insights:

  1. Artifacts are Fragmented: Traditional engineering artifacts are created independently and lack a shared ontology, making them difficult to integrate
  2. Blueprint is the Parent Structure: The blueprint serves as the central model from which other artifacts derive as projections
  3. Transformations Enable Automation: Bidirectional transformations between blueprints and projections enable consistency checking, automated updates, and artifact synchronization
  4. Taxonomy Provides Clarity: A clear taxonomy distinguishes between primary artifacts (blueprint), derived artifacts (projections), and supporting artifacts (context and reasoning)

Practical Guidance:

  • Treat blueprints as primary: Create and maintain blueprints as the central representation of system architecture
  • Generate projections from blueprints: Use blueprints as the source for architecture diagrams, specifications, and runbooks
  • Maintain consistency: Ensure that all artifacts remain consistent with the underlying blueprint
  • Leverage automation: Use tools to generate projections, detect inconsistencies, and synchronize artifacts
