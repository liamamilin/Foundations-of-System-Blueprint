15  Composition: How Systems Are Actually Built

Large software systems are rarely created entirely from original designs.

In practice, most systems are assembled by combining existing architectural patterns, infrastructure components, and service structures. Engineers reuse familiar solutions for authentication, data processing, communication, and orchestration, adapting them to fit the needs of a particular project.

Despite this reality, engineering discussions often describe system design as if each architecture were created from scratch.

The blueprint framework adopts a different perspective.

Instead of treating system design as a process of invention, it treats system design as a process of composition.

Systems are built by combining structural elements, integrating subsystems, and coordinating interactions across architectural boundaries.

Understanding how this composition occurs is therefore essential for blueprint-based engineering.

15.1 Systems Are Built From Patterns

Over time, certain architectural patterns have become widely recognized across the software industry.

The Pattern Recognition Reality

When experienced engineers design systems, they rarely invent entirely new architectures from first principles. Instead, they recognize problems and select appropriate patterns to address them.

Examples include:

  • Layered Architectures: Separating concerns into presentation, application, business, and data layers
  • Microservice Architectures: Decomposing systems into independently deployable services
  • Event-Driven Architectures: Using events to coordinate loosely-coupled components
  • Pipeline Architectures: Organizing processing into sequential stages
  • Repository Patterns: Abstracting data access behind interfaces
  • Circuit Breaker Patterns: Handling failures gracefully in distributed systems

From Patterns to Compositions

While these patterns appear in many different forms, they share common structural principles. Each pattern describes a particular way of organizing components, interfaces, and data flows.

When engineers build large systems, they:

  1. Identify patterns that address the requirements
  2. Adapt patterns to the specific context
  3. Combine patterns into larger compositions
  4. Refine patterns based on implementation experience

A web platform may combine: - A service architecture (microservice pattern) - A messaging system (event-driven pattern) - A data pipeline (pipeline pattern) - A caching layer (repository pattern)

A machine learning platform may combine: - A workflow orchestration pattern - A distributed storage pattern - A model-serving pattern - A data ingestion pattern

In this sense, large systems resemble architectural compositions rather than isolated designs.

Blueprints Make Composition Explicit

Without blueprints, this composition is implicit:

  • Patterns exist in the minds of experienced engineers
  • Composition decisions are made informally during design discussions
  • The resulting architecture is captured in code rather than in structural descriptions

With blueprints, composition becomes explicit:

  • Each pattern can be represented as a blueprint
  • Composition decisions are recorded in the structure of combined blueprints
  • The resulting architecture is captured as a structural model

This explicitness enables:

  • Systematic analysis: Understanding how systems are composed
  • Pattern discovery: Identifying which patterns are used most frequently
  • Composability validation: Checking whether patterns can be combined
  • Composition reuse: Reusing successful compositions in new projects

15.2 Three Modes of Composition

System composition can occur in several distinct ways.

Within the blueprint framework, three primary modes of composition are identified:

  1. Stacking
  2. Coupling
  3. Orchestration

These modes describe different structural relationships between subsystems.

15.2.1 Mode 1: Stacking

Stacking occurs when systems are organized in layers.

The Layered Pattern

In layered architectures, each layer provides services to the layer above while relying on the layer below. This creates a vertical stack of dependencies.

Characteristics of Stacking:

  • Hierarchical organization: Clear hierarchy from low-level to high-level components
  • Upward dependency: Higher layers depend on lower layers, but not vice versa
  • Service provision: Each layer provides specific services to the layer above
  • Abstraction levels: Each layer operates at a different level of abstraction

Examples of Stacking:

Operating Systems:

Application Layer (User applications)
    ↓
System Call Interface
    ↓
Kernel Layer (Process management, memory management, I/O)
    ↓
Hardware Abstraction Layer
    ↓
Hardware (CPU, memory, devices)

Web Application Stack:

Presentation Layer (Web frontend)
    ↓
Application Layer (Business logic services)
    ↓
Data Access Layer (Database access and caching)
    ↓
Data Storage Layer (Databases, file systems)

Cloud Platform Stack:

Platform Services (Developer tools, deployment services)
    ↓
Application Runtime (Containers, serverless functions)
    ↓
Infrastructure Services (Virtual machines, networking, storage)
    ↓
Physical Infrastructure (Data centers, servers)

Blueprint Representation of Stacking:

In a stacked composition, blueprints are combined by:

  1. Identifying layers as distinct subsystems
  2. Defining interfaces between layers (upward service interfaces)
  3. Ensuring dependencies flow downward (higher layers depend on lower layers)
  4. Maintaining layer independence (lower layers don’t depend on higher layers)

Advantages of Stacking:

  • Separation of concerns: Each layer handles a specific concern
  • Modifiability: Layers can be modified without affecting other layers (if interfaces remain stable)
  • Reusability: Lower layers can be reused by multiple higher layers
  • Understandability: The hierarchical structure is easy to understand

Challenges of Stacking:

  • Performance: Calls across layers add latency
  • Rigidity: Changing layer boundaries may require significant refactoring
  • Bypass risk: Engineers may bypass layers, violating the architectural intent
  • Abstraction leakage: Low-level concerns may leak into higher layers

15.2.2 Mode 2: Coupling

Coupling occurs when systems interact through direct dependencies.

The Peer-to-Peer Pattern

In this mode, components communicate with each other through explicit interfaces, forming networks of interacting services or modules. Components are peers rather than being arranged hierarchically.

Characteristics of Coupling:

  • Network structure: Components form a graph of dependencies
  • Bidirectional or multi-directional dependencies: Components may depend on each other
  • Interface-based communication: Interactions occur through defined interfaces
  • Potential for complexity: Dependency networks can become complex

Examples of Coupling:

Microservice Architecture:

Order Service ←→ Payment Service
    ↓              ↓
Inventory Service ←→ Shipping Service

Service Mesh:

Service A ←→ Service B ←→ Service C
    ↓            ↓            ↓
[Service Mesh Infrastructure]

Event-Driven Architecture:

Producer Service → Event Bus → Consumer Service 1
                              → Consumer Service 2
                              → Consumer Service 3

Blueprint Representation of Coupling:

In a coupled composition, blueprints are combined by:

  1. Identifying components as peers in a network
  2. Defining interfaces that components use to interact
  3. Specifying dependency relationships (who depends on whom)
  4. Ensuring interface compatibility across dependencies

Advantages of Coupling:

  • Flexibility: Components can be added, removed, or replaced independently
  • Scalability: Individual components can be scaled based on demand
  • Technology diversity: Different components can use different technologies
  • Organizational alignment: Components can align with team boundaries

Challenges of Coupling:

  • Complexity: Managing dependencies and interactions becomes complex
  • Consistency: Ensuring data consistency across components is challenging
  • Observability: Understanding system behavior requires tracing interactions across components
  • Testing: Integration testing becomes more complex

15.2.3 Mode 3: Orchestration

Orchestration occurs when a coordinating component manages the execution of multiple subsystems.

The Controller Pattern

In orchestration-based architectures, a central controller determines the sequence in which tasks are executed and coordinates interactions between subsystems.

Characteristics of Orchestration:

  • Central coordination: A controller orchestrates subsystem execution
  • Defined workflows: The controller specifies workflows or sequences of operations
  • State management: The controller often maintains workflow state
  • Error handling: The controller handles failures and retries

Examples of Orchestration:

Workflow Engine:

Workflow Controller
    ↓
    ├→ Task 1 (Data Ingestion)
    ├→ Task 2 (Data Validation)
    ├→ Task 3 (Data Transformation)
    └→ Task 4 (Data Loading)

Job Scheduler:

Scheduler
    ↓
    ├→ Job 1 (Backup) → Worker A
    ├→ Job 2 (Report Generation) → Worker B
    └→ Job 3 (Data Cleanup) → Worker C

CI/CD Pipeline:

Pipeline Orchestrator
    ↓
    ├→ Build Stage → Build Worker
    ├→ Test Stage → Test Workers
    ├→ Deploy Stage → Deploy Worker
    └→ Monitor Stage → Monitoring System

Blueprint Representation of Orchestration:

In an orchestrated composition, blueprints are combined by:

  1. Identifying a controller blueprint (orchestrator)
  2. Identifying worker blueprints (subsystems being orchestrated)
  3. Defining control interfaces (how the controller triggers workers)
  4. Defining status interfaces (how workers report back to the controller)
  5. Specifying workflow definitions (sequences of operations)

Advantages of Orchestration:

  • Clear control flow: Workflows are explicitly defined and easy to understand
  • Error handling: Centralized error handling and retry logic
  • Monitoring: Workflow progress and status are centrally tracked
  • Flexibility: Workflows can be modified without changing subsystems

Challenges of Orchestration:

  • Centralization risk: The controller can become a bottleneck or single point of failure
  • Complexity: Complex workflows may be difficult to define and maintain
  • Coupling: Subsystems may become coupled to the orchestrator’s interface
  • Scalability: Orchestrating many subsystems may require careful performance tuning

Comparing the Three Modes

Mode Structure Dependency Flow Typical Use Case Key Challenge
Stacking Hierarchical layers Downward (higher depends on lower) Organizing systems by abstraction level Layer rigidity, performance
Coupling Peer network Multi-directional Service-oriented architectures Dependency complexity
Orchestration Controller + workers Controller to workers Workflow and batch processing Controller bottleneck

Systems often use multiple modes simultaneously. For example, a microservice architecture (coupling) may have internal layering (stacking) and be orchestrated by a workflow engine (orchestration).

15.3 Conflicts in System Composition

Although combining subsystems is essential for building complex systems, composition introduces several challenges.

When two architectural structures are combined, conflicts may arise in multiple dimensions.

The Three Categories of Composition Conflicts

15.3.1 Category 1: Interface Conflicts

Interfaces define how components interact. When combining blueprints, interfaces must be compatible.

Types of Interface Conflicts:

  • Protocol mismatch: One system uses HTTP, another uses gRPC or message queues
  • Data format mismatch: One system uses JSON, another uses XML or Protocol Buffers
  • Operation mismatch: Required operations are not available or have different signatures
  • Version mismatch: Different versions of the same interface are incompatible
  • Semantic mismatch: Same operation name but different behavior or semantics

Example Conflict:

When integrating a Payment Service blueprint with an Order Service blueprint:

  • Order Service expects: processPayment(orderId, amount, paymentMethod)
  • Payment Service provides: authorizeTransaction(cardInfo, amount) and captureTransaction(transactionId)

The interfaces don’t match, requiring an adapter or integration layer.

Resolution Strategies:

  • Adapter pattern: Create an adapter that translates between incompatible interfaces
  • Interface modification: Modify one or both interfaces to achieve compatibility
  • Facade pattern: Create a facade that provides a unified interface to multiple subsystems
  • Protocol gateway: Use a gateway to translate between different protocols

15.3.2 Category 2: Data Conflicts

Data conflicts arise when subsystems use different data models, ownership rules, or consistency guarantees.

Types of Data Conflicts:

  • Model mismatch: Different representations of the same entity
  • Ownership conflicts: Conflicting claims about who owns or manages data
  • Consistency mismatch: Different consistency guarantees (strong vs. eventual consistency)
  • Schema evolution: Incompatible schema versions
  • Naming conflicts: Same name used for different entities or different names for the same entity

Example Conflict:

When combining a User Service blueprint with an Order Service blueprint:

  • User Service defines: User { id, name, email, address }
  • Order Service defines: User { userId, customerName, shippingAddress }

The user model is represented differently in each system, causing integration challenges.

Resolution Strategies:

  • Canonical data model: Establish a shared data model that all systems use for integration
  • Data transformation: Transform data between different models as it flows between systems
  • Data ownership agreements: Clearly define which system owns which data
  • Event-driven synchronization: Use events to keep data synchronized across systems
  • API-based access: Access data through APIs rather than sharing databases directly

15.3.3 Category 3: Constraint Conflicts

Constraints define the limitations and requirements that systems must satisfy. When combining blueprints, constraints may conflict.

Types of Constraint Conflicts:

  • Performance conflicts: One system requires low latency, another requires high throughput
  • Reliability conflicts: Different availability or durability requirements
  • Security conflicts: Different security models or compliance requirements
  • Scalability conflicts: Different scaling assumptions or requirements
  • Resource conflicts: Competing for limited resources (CPU, memory, network)

Example Conflict:

When combining a real-time analytics blueprint with a batch processing blueprint:

  • Real-time analytics requires: Low latency (< 100ms), high availability (99.99%)
  • Batch processing requires: High throughput, cost efficiency

These constraints may conflict when both run on shared infrastructure.

Resolution Strategies:

  • Resource allocation: Allocate dedicated resources to satisfy conflicting constraints
  • Priority negotiation: Establish priorities when constraints cannot all be satisfied
  • Architecture separation: Separate systems with conflicting constraints into different deployment environments
  • Constraint relaxation: Negotiate relaxed constraints where possible
  • Technology selection: Choose technologies that can satisfy multiple constraints

The Complexity of Multi-Dimensional Conflicts

Real-world composition often involves conflicts across multiple dimensions simultaneously. For example:

  • Interface conflicts (protocol mismatch)
  • AND data conflicts (model mismatch)
  • AND constraint conflicts (performance vs. security trade-offs)

Resolving these multi-dimensional conflicts requires:

  • Systematic analysis: Understanding all conflicts and their interactions
  • Prioritization: Determining which conflicts are most critical
  • Iterative resolution: Addressing conflicts in order of priority
  • Architecture refactoring: Sometimes requiring changes to the original blueprints

15.4 Toward Rules for Blueprint Composition

If blueprints represent system structures in a consistent format, it becomes possible to define rules governing how those structures can be combined.

Such rules may address questions such as:

  • Which interfaces must align when two systems interact?
  • How should data ownership be managed across subsystems?
  • What constraints must be satisfied when combining architectural patterns?
  • How can conflicts be detected and resolved automatically?

The Composition Contract

For blueprints to be composable, they must satisfy a composition contract:

  1. Interface Compatibility: Interfaces must be compatible or translatable
  2. Data Consistency: Data models must be aligned or transformable
  3. Constraint Satisfaction: Combined constraints must be satisfiable
  4. Semantic Alignment: Intent and capabilities must not conflict

Composition Operations

Blueprint composition can be expressed through formal operations:

  • Merge: Combine two blueprints into one (e.g., combining capabilities)
  • Compose: Connect blueprints through interfaces (e.g., service composition)
  • Overlay: Layer one blueprint over another (e.g., adding monitoring to a service)
  • Extract: Extract a subsystem blueprint from a larger blueprint
  • Transform: Modify a blueprint to achieve compatibility

Automated Composition Rules

Future volumes in this series will explore composition rules in detail, including:

  • Interface matching algorithms: Automatically determining interface compatibility
  • Data model alignment: Detecting and resolving data model conflicts
  • Constraint satisfaction: Checking whether combined constraints are satisfiable
  • Composition validation: Ensuring composed systems maintain architectural quality
  • Composition optimization: Finding optimal compositions based on requirements

The Goal: Predictable Composition

The ultimate goal is to make blueprint composition predictable and systematic:

  • Engineers can determine whether two blueprints can be composed
  • Tools can automatically detect and suggest resolutions for conflicts
  • Composition decisions can be validated before implementation
  • Composed systems can be analyzed for quality and correctness

This goal represents a significant advancement over current practice, where composition is often ad-hoc and error-prone.

15.5 Blueprint as the Minimal Composition Interface

For composition to work reliably, participating systems must share a common representation of their structure.

Blueprints provide this representation.

The Common Representation

Because each blueprint describes its system using consistent structural elements—components, interfaces, data relationships, workflows, and constraints—blueprints function as a minimal common interface for architectural composition.

What Makes Blueprints a Good Composition Interface?

  1. Explicit Structure: All structural elements are explicitly defined, not inferred
  2. Consistent Schema: All blueprints use the same kernel structure
  3. Standardized Elements: Components, interfaces, data, and workflows are represented consistently
  4. Machine-Usable: Structure can be parsed and analyzed by tools
  5. Extensible: Additional information can be added without breaking compatibility

The Composition Workflow

With blueprints as the common interface, composition follows a systematic workflow:

1. Retrieve blueprint A
2. Retrieve blueprint B
3. Analyze compatibility:
   - Check interface compatibility
   - Check data model alignment
   - Check constraint satisfaction
4. Resolve conflicts:
   - Apply adapters or transformations
   - Negotiate constraints
   - Align data models
5. Validate composition:
   - Verify composed structure is valid
   - Check quality criteria
6. Implement composition

Beyond Manual Composition

The blueprint model enables not just manual composition but also:

  • Automated composition: Tools can automatically compose compatible blueprints
  • Composition search: Find optimal compositions from a library of blueprints
  • Composition validation: Validate compositions before implementation
  • Composition optimization: Optimize compositions based on constraints

15.6 Summary: Composition as the Reality of System Building

This chapter has established that composition, not invention, is the primary reality of system building.

Key Insights:

  1. Systems are built from patterns: Engineers reuse architectural patterns rather than inventing new architectures from scratch
  2. Three composition modes: Stacking (layered), coupling (peer-to-peer), and orchestration (controller-worker) describe different ways systems are combined
  3. Conflicts are inevitable: Interface, data, and constraint conflicts arise when combining systems and must be resolved
  4. Blueprints enable systematic composition: Structured representations make composition predictable and automatable
  5. Composition is the foundation of scale: Complex systems are built through composition of simpler components

Practical Implications:

  • Design for composition: When creating blueprints, consider how they will be combined with other blueprints
  • Use standard interfaces: Adhere to interface standards to enable composition
  • Document constraints explicitly: Make constraints clear to enable conflict detection
  • Leverage composition patterns: Understand and reuse proven composition patterns
  • Invest in composition tooling: Build tools that support blueprint composition

The Road Ahead:

This chapter introduces the concept of blueprint composition, but many questions remain:

  • How can composition be automated at scale?
  • What formal rules govern valid compositions?
  • How can composition conflicts be resolved systematically?
  • How can we discover optimal compositions?

These questions will be addressed in future volumes of the series, particularly in the volume dedicated to System Composition.

15.6.1 Knowledge Summary

The following concepts are the core of this chapter — you must understand and remember them:

  1. Systems are built from patterns, not invented from scratch: Experienced engineers recognize problems and select appropriate patterns (layered, microservice, event-driven, pipeline, etc.). Large systems are architectural compositions — combinations of multiple patterns — not isolated inventions.

  2. Three modes of composition:

    Mode Structure Dependency Flow Example
    Stacking Hierarchical layers Downward (higher depends on lower) OS kernel → OS → Application
    Coupling Peer-to-peer network Multi-directional Microservice architecture
    Orchestration Controller + workers Controller to workers CI/CD pipeline, workflow engine

    Most real systems use multiple modes simultaneously.

  3. Three categories of composition conflicts:

    • Interface conflicts: Protocol mismatch, data format mismatch, operation mismatch, version mismatch, semantic mismatch
    • Data conflicts: Model mismatch, ownership conflicts, consistency mismatch, schema evolution, naming conflicts
    • Constraint conflicts: Performance, reliability, security, scalability, and resource conflicts

    Resolution strategies include adapter pattern, canonical data model, resource allocation, and architecture separation.

  4. The composition contract: For blueprints to be composable, four conditions must be satisfied: (1) Interface Compatibility — interfaces are compatible or translatable, (2) Data Consistency — data models are aligned or transformable, (3) Constraint Satisfaction — combined constraints are satisfiable, (4) Semantic Alignment — intent and capabilities do not conflict.

  5. Blueprint as the minimal composition interface: Because each blueprint describes its system using consistent structural elements (components, interfaces, data, workflows, constraints), blueprints function as a common representation for architectural composition. This enables systematic, predictable, and eventually automatable composition.
