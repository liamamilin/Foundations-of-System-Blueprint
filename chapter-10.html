13  Classification: Types, Levels, Complexity

Once blueprints are represented as structured knowledge objects, another question immediately arises: how should they be organized?

A collection of blueprints without classification quickly becomes difficult to navigate. Engineers may possess a large number of architectural descriptions, but without a consistent taxonomy, locating relevant designs becomes inefficient.

Classification therefore plays a critical role in blueprint-based engineering.

By assigning each blueprint a clear position within a classification system, architectural knowledge can be indexed, searched, and reused systematically.

This chapter introduces a three-dimensional classification framework for organizing blueprints. The framework categorizes systems along three axes:

  • System Type
  • Blueprint View
  • Complexity Tier

Together, these axes provide a navigational structure for architectural knowledge repositories.

13.1 Why Classification Is Necessary

In many engineering environments, architectural knowledge accumulates without a formal structure.

The Problem of Unorganized Knowledge

Documentation repositories contain a wide range of materials: design documents, architecture diagrams, decision records, and implementation notes. While these artifacts may contain valuable insights, they are rarely organized according to a consistent taxonomy.

As a result, engineers often struggle to locate relevant architectural examples when designing new systems.

The Search Problem

When searching for architectural patterns, engineers face several challenges:

  • Terminology inconsistency: Similar patterns are described using different terms
  • Context ambiguity: It’s unclear whether an example is relevant to a particular problem
  • Scale mismatch: An example may be too simple or too complex for the problem at hand
  • Domain incompatibility: An example from a different domain may not apply directly

Without a classification system, finding relevant architectures requires:

  • Manual browsing through many documents
  • Reading each document to determine relevance
  • Guessing which keywords or tags might lead to useful examples
  • Relying on informal knowledge of what documents exist

The Consequences of Poor Classification

Poor classification has measurable consequences:

  • Rediscovery: Teams repeatedly solve similar problems because they cannot find existing solutions
  • Inconsistency: Similar systems are designed differently because there’s no shared reference
  • Isolation: Architectural knowledge remains within teams or individuals rather than spreading across the organization
  • Loss: Valuable architectural insights are lost when documents are forgotten or when people leave the organization

The Solution: Organized Architectural Knowledge

A classification system addresses these problems by organizing architectural knowledge into predictable categories.

When blueprints are classified consistently, engineers can:

  • Retrieve examples of similar systems quickly
  • Compare alternative architectures within the same category
  • Understand patterns that apply to specific system types
  • Learn from examples that match their problem’s scale and complexity

Classification therefore transforms blueprint repositories from static collections of documents into searchable architectural libraries.

13.2 The Three-Dimensional Classification Framework

The blueprint framework introduces a three-dimensional coordinate system for organizing blueprints.

The Three Classification Axes:

Axis Description Purpose
System Type What kind of system is represented Group similar architectural patterns
Blueprint View What perspective the blueprint emphasizes Organize for different audiences
Complexity Tier How large or complex the system is Match examples to problem scale

Together, these axes form a navigational map for blueprint repositories.

Visualizing the Classification Space

Imagine a three-dimensional space where each blueprint is located at coordinates (X, Y, Z):

  • X-axis: System Type (CLI, Web, API, Workflow, Pipeline, Agent, Platform)
  • Y-axis: Blueprint View (Product, Technical, Operational)
  • Z-axis: Complexity Tier (Toy, Small, Medium, Large)

For example, a blueprint might be located at (Web, Technical, Medium)—a medium-scale web application described through a technical view.

Why Three Dimensions?

A single dimension is insufficient to capture the relevant characteristics of blueprints:

  • System Type alone doesn’t tell you whether a blueprint is appropriate for your complexity level
  • View alone doesn’t tell you what kind of system is being described
  • Complexity alone doesn’t tell you whether the blueprint applies to your system type

Three dimensions provide a richer, more precise classification that supports effective retrieval and comparison.

13.3 Axis 1: System Types

The first axis of classification describes the type of system represented by a blueprint.

Different types of systems exhibit distinct architectural patterns. Recognizing these categories allows engineers to identify relevant blueprint examples more quickly.

The Initial System Type Taxonomy

The initial taxonomy introduced in this framework includes seven common system types:

13.3.1 CLI Tools

Command-line tools are systems designed to be invoked through a textual interface.

Characteristics: - Interaction model: Command-line arguments, flags, and configuration files - Execution model: Often run as single processes with short lifetimes - State model: May maintain local state or interact with persistent storage - Complexity range: Typically small to medium

Common Architectural Patterns: - Command parser → command dispatcher → handler modules - Pipeline architectures for data processing - Plugin systems for extensibility

Typical Kernel Emphasis: - Goal: Automate specific tasks or operations - Capabilities: Set of commands with defined behaviors - Components: Parser, dispatcher, handlers, file/system interfaces - Interfaces: Command-line arguments, configuration files, stdin/stdout - Data: Input/output data, configuration state - Workflows: Command execution sequences, error handling

Examples: File compression tools, build systems, deployment utilities

13.3.2 Web Applications

Web applications provide interactive functionality through web interfaces.

Characteristics: - Interaction model: HTTP requests/responses, often with stateful sessions - Execution model: Long-running services handling concurrent requests - State model: Session state, persistent data in databases - Complexity range: Small to large

Common Architectural Patterns: - Three-tier architecture (frontend, backend, database) - Microservice architectures for larger applications - Event-driven systems for real-time features

Typical Kernel Emphasis: - Goal: Provide user-facing functionality through web interfaces - Capabilities: User actions, data management, interactions - Components: Frontend, backend services, databases, caches - Interfaces: HTTP APIs, websockets, database connections - Data: User data, application state, content - Workflows: Request processing, authentication flows, data updates

Examples: Content management systems, collaboration platforms, e-commerce sites

13.3.3 APIs and Services

API-based systems expose functionality through service interfaces.

Characteristics: - Interaction model: Programmatic access through defined interfaces - Execution model: Often long-running services in distributed environments - State model: May be stateless or manage state externally - Complexity range: Small to large

Common Architectural Patterns: - Service-oriented architectures - RESTful or gRPC interfaces - Event-driven service communication

Typical Kernel Emphasis: - Goal: Expose capabilities to other systems or applications - Capabilities: Service operations, data access, computations - Components: Service implementations, gateways, authentication - Interfaces: API endpoints, message queues, event streams - Data: Request/response schemas, internal state - Workflows: Request processing, service orchestration, error handling

Examples: Authentication services, data access APIs, notification services

13.3.4 Workflow Engines

Workflow systems coordinate sequences of tasks or processes.

Characteristics: - Interaction model: Define, trigger, and monitor workflows - Execution model: Manage task execution and state transitions - State model: Workflow definitions, execution state, task history - Complexity range: Medium to large

Common Architectural Patterns: - Orchestrator patterns with task coordination - State machine implementations for workflow states - Event-driven task execution

Typical Kernel Emphasis: - Goal: Coordinate complex multi-step processes - Capabilities: Workflow definition, execution, monitoring - Components: Workflow engine, task executors, state store - Interfaces: Workflow definition APIs, execution APIs, monitoring APIs - Data: Workflow definitions, execution state, task results - Workflows: Workflow lifecycle, task execution sequences, error recovery

Examples: Job schedulers, process automation platforms, CI/CD systems

13.3.5 Data Pipelines

Data pipeline systems process and transform data across multiple stages.

Characteristics: - Interaction model: Ingest, transform, and output data - Execution model: Batch or stream processing - State model: Data state, processing state, lineage information - Complexity range: Medium to large

Common Architectural Patterns: - Pipeline architectures with sequential stages - Directed acyclic graphs (DAGs) for processing dependencies - Lambda architectures for batch and stream processing

Typical Kernel Emphasis: - Goal: Process and transform data reliably - Capabilities: Data ingestion, transformation, enrichment, loading - Components: Ingestion layers, transformation engines, storage systems - Interfaces: Data source connectors, data sink connectors, configuration APIs - Data: Input schemas, output schemas, intermediate data, lineage metadata - Workflows: Processing pipelines, error handling, retry logic

Examples: ETL systems, analytics pipelines, real-time data processing

13.3.6 Agent Systems

Agent-based systems coordinate autonomous components capable of performing tasks, making decisions, or interacting with external environments.

Characteristics: - Interaction model: Goal-directed autonomous behavior - Execution model: Continuous operation with task scheduling - State model: Agent state, environment state, planning state - Complexity range: Medium to large

Common Architectural Patterns: - Multi-agent coordination patterns - Planning and execution architectures - Perception-action loops

Typical Kernel Emphasis: - Goal: Achieve objectives through autonomous behavior - Capabilities: Task planning, execution, learning, adaptation - Components: Planning modules, execution engines, perception systems, memory systems - Interfaces: Task interfaces, environment interfaces, tool interfaces - Data: Task representations, world models, experience data - Workflows: Planning cycles, execution loops, learning processes

Examples: Autonomous agents, AI assistants, robotics systems

13.3.7 Platforms

Platforms provide infrastructure or capabilities that support other systems.

Characteristics: - Interaction model: Provide capabilities to multiple applications or tenants - Execution model: Highly available, scalable infrastructure - State model: Multi-tenant state, platform state, application state - Complexity range: Large

Common Architectural Patterns: - Multi-tenant architectures - Service mesh and platform services - Extensibility frameworks

Typical Kernel Emphasis: - Goal: Provide a foundation for building or running applications - Capabilities: Infrastructure services, development tools, runtime environments - Components: Service layers, platform services, management systems - Interfaces: Platform APIs, developer portals, integration hooks - Data: Platform metadata, tenant data, usage data - Workflows: Provisioning workflows, deployment workflows, scaling operations

Examples: Cloud platforms, developer platforms, data infrastructure platforms

The Taxonomy is Extensible

This initial taxonomy covers common system types but is not exhaustive. New system types can be added as needed:

  • Mobile applications
  • Gaming systems
  • Blockchain systems
  • IoT systems
  • Scientific computing systems

The taxonomy provides a starting point that can be extended to capture new patterns as they emerge.

13.4 Axis 2: Blueprint Views

While system types describe what kind of system is represented, blueprints can also be categorized according to the perspective they emphasize.

Different stakeholders require different views of the same system. The blueprint framework therefore distinguishes between several blueprint types.

13.4.1 Product View Blueprint

Product view blueprints emphasize the capabilities and goals of the system.

They focus on what the system provides to users or other systems rather than on how those capabilities are implemented internally.

Characteristics: - Emphasis on goals, success criteria, and capabilities - Minimal focus on implementation details - User-centric language and descriptions

Audience: Product managers, stakeholders, designers, end users

Use Cases: - Product planning and requirement gathering - Stakeholder communication and alignment - User experience design - Feature prioritization

Kernel Emphasis: - Goal: Detailed description of objectives and success criteria - Capabilities: Functional requirements and user-facing features - Constraints: User constraints, performance requirements, compliance requirements - Other elements: Minimal structural detail, focused on outcomes

13.4.2 Technical View Blueprint

Technical view blueprints emphasize the structural architecture of the system.

They describe components, interfaces, dependencies, and communication mechanisms.

Characteristics: - Emphasis on components, interfaces, and dependencies - Technical precision in describing structures and relationships - Implementation-oriented but not implementation-specific

Audience: Architects, senior engineers, technical leads

Use Cases: - System design and architecture reviews - Implementation planning and coordination - Technical decision-making - Code organization and structure

Kernel Emphasis: - Components: Detailed component structure and responsibilities - Interfaces: Precise interface definitions and contracts - Data: Data models and relationships - Workflows: Component interaction patterns - Other elements: Balanced emphasis across all structural elements

13.4.3 Operational View Blueprint

Operational view blueprints emphasize the runtime behavior of the system.

They describe workflows, operational processes, deployment structures, and monitoring considerations.

Characteristics: - Emphasis on workflows, procedures, and runtime behavior - Focus on reliability, scalability, and observability - Operational metrics and performance characteristics

Audience: Operations teams, DevOps engineers, support teams, SREs

Use Cases: - Production deployment and maintenance - Troubleshooting and incident response - Capacity planning and scaling - Monitoring and alerting configuration

Kernel Emphasis: - Workflows: Detailed operational workflows and procedures - Components: Deployment units and operational boundaries - Interfaces: Monitoring interfaces, management APIs - Constraints: Performance targets, reliability requirements, operational limits - Other elements: Strong emphasis on operational aspects

Multiple Views of the Same System

It’s important to note that these are not different blueprints—they are different views of the same blueprint. A single system blueprint can generate:

  • A product view for stakeholders
  • A technical view for architects and engineers
  • An operational view for operations teams

All three views derive from the same underlying blueprint model, ensuring consistency across perspectives.

13.5 Axis 3: Complexity Tiers

The third axis of classification describes the scale and complexity of the system.

Systems vary widely in size and organizational complexity. A simple utility tool requires a very different architectural structure from a large distributed platform.

To capture these differences, blueprints can be categorized into four complexity tiers.

13.5.1 Toy Systems

Toy systems are minimal examples designed primarily for demonstration or experimentation.

Characteristics: - Minimal functionality, often demonstrating a single concept - Simplified assumptions and constraints - Not intended for production use - Typically implemented by a single person

Complexity Indicators: - 1-3 components - Simple or no interfaces - Minimal data structures - Straightforward workflows - No significant operational concerns

Use Cases: - Learning and education - Proof of concept - Architecture exploration - Tool development

Example: A “Hello World” service, a simple calculator CLI, a basic to-do list application

13.5.2 Small Systems

Small systems typically consist of a limited number of components and can often be maintained by a small team.

Characteristics: - Focused functionality addressing specific needs - Simple component structure with clear boundaries - Straightforward deployment and operations - Can be maintained by 1-5 engineers

Complexity Indicators: - 3-10 components - Well-defined interfaces between components - Moderate data complexity - Clear workflow structures - Basic operational requirements

Use Cases: - Internal tools and utilities - Small business applications - Single-purpose services - Prototype systems

Example: A file compression tool, a small web application, an API service with limited scope

13.5.3 Medium Systems

Medium systems involve multiple subsystems and require more structured architectural coordination.

Characteristics: - Broader functionality requiring multiple capabilities - Complex component relationships and dependencies - Requires architectural planning and coordination - Typically maintained by 5-20 engineers

Complexity Indicators: - 10-50 components across multiple subsystems - Multiple interface protocols and integration points - Complex data models and relationships - Multi-step workflows with branching and error handling - Significant operational requirements (scaling, reliability, monitoring)

Use Cases: - Production web applications - Business-critical services - Multi-tenant platforms - Data processing systems

Example: An e-commerce platform, a content management system, a data analytics pipeline

13.5.4 Large Systems

Large systems consist of many interacting services or modules and often require dedicated architectural governance.

Characteristics: - Extensive functionality spanning multiple domains - Highly distributed with many interdependent components - Requires formal architecture processes and governance - Maintained by teams of 20+ engineers, often across multiple teams

Complexity Indicators: - 50+ components across many subsystems - Complex interface ecosystems with versioning and evolution - Large-scale data management with multiple data stores - Sophisticated workflows with coordination across services - Demanding operational requirements (global scale, high availability, strict SLAs)

Use Cases: - Global platforms serving millions of users - Enterprise systems with complex integrations - Multi-product platforms - Critical infrastructure systems

Example: Cloud platforms, large-scale social networks, enterprise ERP systems, global payment networks

Complexity is Multi-Dimensional

These tiers represent guidelines rather than strict boundaries. Complexity has multiple dimensions:

  • Structural complexity: Number of components, relationships, and interfaces
  • Behavioral complexity: Complexity of workflows and dynamic behavior
  • Operational complexity: Deployment, scaling, and monitoring requirements
  • Organizational complexity: Number of teams, coordination needs, governance requirements

A system may score high on some dimensions and low on others. The complexity tier should reflect the overall architectural complexity rather than a single metric.

13.6 The Three-Dimensional Blueprint Map

Together, the three axes introduced in this chapter form a three-dimensional classification space.

Coordinate System

Each blueprint can be located within this space according to:

  • X-coordinate: System Type (CLI, Web, API, Workflow, Pipeline, Agent, Platform)
  • Y-coordinate: Blueprint View (Product, Technical, Operational)
  • Z-coordinate: Complexity Tier (Toy, Small, Medium, Large)

Example Coordinates

  • (CLI, Technical, Small): A small command-line tool described through a technical view
  • (Web, Product, Medium): A medium-scale web application described through a product view
  • (API, Operational, Large): A large-scale API service described through an operational view
  • (Pipeline, Technical, Medium): A medium-scale data pipeline described through a technical view
  • (Agent, Product, Small): A small agent system described through a product view

Navigation and Retrieval

This coordinate system provides a navigational map for blueprint repositories:

  • Retrieve by type: Find all blueprints for a specific system type
  • Retrieve by view: Find blueprints that match your perspective
  • Retrieve by complexity: Find blueprints that match your problem’s scale
  • Combine filters: Find blueprints that match multiple criteria

Example: Finding a Relevant Blueprint

Suppose you’re designing a medium-scale web application. You would:

  1. Navigate to X = Web (system type)
  2. Navigate to Z = Medium (complexity tier)
  3. Choose Y based on your current need (Product for requirements, Technical for design, Operational for deployment)

The blueprints in that region of the space are most relevant to your problem.

Benefits of the Classification System

The three-dimensional map provides several benefits:

  • Efficient retrieval: Quickly locate relevant architectural examples
  • Pattern recognition: Identify common patterns within each region of the space
  • Comparison: Compare alternative architectures within the same classification
  • Evolution tracking: Track how architectures evolve across complexity tiers

13.7 Summary: The Classification Framework

This chapter has introduced a comprehensive classification framework for organizing blueprint knowledge.

Key Components:

  1. System Types: Seven categories (CLI, Web, API, Workflow, Pipeline, Agent, Platform) that group similar architectural patterns
  2. Blueprint Views: Three perspectives (Product, Technical, Operational) that organize blueprints for different audiences
  3. Complexity Tiers: Four levels (Toy, Small, Medium, Large) that categorize systems by scale and complexity

The Three-Dimensional Space:

These axes combine to form a navigational map where each blueprint has coordinates (System Type, Blueprint View, Complexity Tier).

Practical Benefits:

  • Efficient retrieval: Find relevant architectural examples quickly
  • Consistent organization: Maintain a structured blueprint repository
  • Pattern discovery: Identify architectural patterns within specific classifications
  • Scalable organization: Accommodate growing collections of blueprints

Foundation for Future Work:

This classification framework provides the structural foundation for later volumes in this series, which will introduce:

  • Pattern libraries organized by system type and complexity
  • Composition rules based on system compatibility
  • Architectural datasets built upon this taxonomy
  • Search and retrieval systems that leverage this structure
