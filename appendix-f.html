27  Appendix F — Projection Map

27.1 Blueprint → Architecture View / Spec View / Ops View

One of the central ideas of the blueprint framework is that a system should be represented by a single structural model from which multiple views can be derived.

In traditional engineering workflows, different artifacts are created independently. Architecture diagrams, specifications, and operational runbooks are often written separately and maintained by different teams. Over time these artifacts drift apart, leading to inconsistencies and misunderstandings.

The blueprint model addresses this problem by treating these artifacts as projections of a single blueprint.

A projection is a view derived from the underlying blueprint that emphasizes a particular aspect of the system.

This appendix provides a comprehensive map of the major projections used in blueprint-based system engineering, including: - The conceptual projection model - Detailed descriptions of each major projection - Mapping of blueprint elements to projections - Practical generation methods - Use cases and benefits - Tool integration guidance - Common pitfalls and best practices

27.2 The Projection Concept

27.2.1 Definition

A projection is a derived representation of a blueprint that highlights a particular aspect of the system while maintaining consistency with the underlying model. Different projections serve different audiences and purposes.

27.2.2 Why Projections Matter

Problem: Traditional documentation creates multiple independent artifacts that drift apart over time.

Solution: Projections are always derived from the same blueprint, ensuring consistency.

Benefit: Teams get the right view for their needs without maintaining separate documents.

27.2.3 The Core Principle

The blueprint is the source of structural truth. All other artifacts are views derived from this central model.

This principle shifts architectural documentation from maintaining multiple documents to maintaining a single model and deriving specialized views.

27.3 The Projection Model

27.3.1 Conceptual Diagram

                    Blueprint (Core System Model)
                                │
                ┌───────────────┼───────────────┐
                │               │               │
                ▼               ▼               ▼
         Architecture View  Spec View  Operational View
         (Structure)       (Behavior)     (Runtime)
                │               │               │
                └───────────────┼───────────────┘
                                │
                                ▼
                    Consistency Guaranteed

27.3.2 Projection Hierarchy

  1. Source Model: Blueprint (kernel + extensions)
  2. Primary Projections: Architecture, Specification, Operational
  3. Derived Views: Specialized views for specific audiences (e.g., security, performance)
  4. Artifacts: Concrete deliverables (diagrams, docs, configs)

27.3.3 Key Characteristics

All projections share these characteristics:

  • Derived: Generated from blueprint, not created independently
  • Consistent: Always aligned with underlying blueprint
  • Focused: Emphasize specific aspects of the system
  • Audience-Specific: Tailored to particular stakeholders
  • Traceable: Can be traced back to blueprint elements

27.4 Architecture View

27.4.1 Definition

The Architecture View focuses on the structural relationships between system components. It answers “How is the system structured?”

27.4.2 Primary Audience

  • Software Architects: Design system structure
  • Technical Leads: Understand component relationships
  • Engineers: Navigate code organization
  • System Integrators: Plan integration points

27.4.3 What It Emphasizes

  • Components and their responsibilities
  • Interfaces and communication boundaries
  • Dependencies and coupling
  • Structural boundaries (internal vs external)
  • Technology choices (at architectural level)

27.4.4 Typical Representations

  • Component Diagrams: Boxes and arrows showing components and interfaces
  • Service Dependency Graphs: Dependency relationships between services
  • System Topology Diagrams: Physical or logical deployment structure
  • Layer Diagrams: Architectural layers and their relationships

27.4.5 Example Architecture View

┌─────────────┐         HTTP/REST          ┌─────────────┐
│   Web       │ ─────────────────────────► │   API       │
│  Frontend   │ ◄───────────────────────── │  Service    │
└─────────────┘    Session Tokens          └─────────────┘
                                               │
                                               │ PostgreSQL
                                               ▼
                                       ┌─────────────┐
                                       │  Database   │
                                       └─────────────┘

Key Elements Shown:
- Components (Frontend, API Service, Database)
- Interfaces (HTTP/REST, PostgreSQL)
- Communication patterns (request/response)
- Technology choices (implied by interface types)

27.4.6 Architecture View Content

Based on blueprint elements:

Blueprint Element Architecture View Representation
Components Nodes/boxes in diagram
Interfaces Arrows/lines between nodes
Interface Protocols Labels on arrows (HTTP, gRPC, etc.)
Component Responsibilities Annotations or detailed diagrams
External Components Distinct visual representation
System Boundaries Enclosing boxes or zones

27.4.7 Generation Method

  1. Extract Components: Read components: section from blueprint
  2. Extract Interfaces: Read interfaces: section
  3. Build Graph: Create nodes for components, edges for interfaces
  4. Apply Layout: Arrange components logically (layered, hierarchical, etc.)
  5. Add Labels: Annotate with protocols, responsibilities, technology
  6. Format Output: Generate diagram (Mermaid, PlantUML, etc.)

27.4.8 Architecture View Checklist

When generating or reviewing architecture views:

27.4.9 Common Pitfalls

❌ Including Behavioral Details: Architecture views should show structure, not workflows or behavior ❌ Implementation-Level Detail: Architecture is at component level, not class or function level ❌ Missing Interfaces: All communication should have defined interfaces ❌ Confusing Layout with Structure: Diagram layout doesn’t equal architectural structure

27.5 Specification View

27.5.1 Definition

The Specification View focuses on system behavior and expected outcomes. It answers “What should the system do and how should it behave?”

27.5.2 Primary Audience

  • Product Managers: Define requirements and acceptance criteria
  • QA Engineers: Create test cases and verify behavior
  • API Consumers: Integrate with system APIs
  • Business Stakeholders: Understand system capabilities

27.5.3 What It Emphasizes

  • Capabilities and their descriptions
  • Interface contracts (API specs, message formats)
  • Input/output behavior
  • Acceptance criteria and success conditions
  • Error conditions and responses
  • Performance and reliability requirements

27.5.4 Typical Representations

  • API Specifications: OpenAPI/Swagger documents
  • Functional Requirements: User stories and acceptance criteria
  • Behavior Specifications: State machines, decision tables
  • Contract Documents: SLAs, SLOs, performance guarantees

27.5.5 Example Specification View

# API Specification: User Authentication

capability: user_authentication

endpoints:
  /auth/login:
    method: POST
    description: Authenticate user and return session token
    request:
      email: string (required)
      password: string (required)
    response:
      success:
        status: 200
        body:
          token: string (JWT)
          user_id: string (UUID)
          expires_at: timestamp
      errors:
        401: Invalid credentials
        400: Invalid input
        429: Rate limit exceeded

  /auth/logout:
    method: POST
    description: Invalidate session token
    request:
      token: string (JWT, header)
    response:
      success:
        status: 200
        body:
          message: "Logged out successfully"
      errors:
        401: Invalid or expired token

acceptance_criteria:
  - Valid credentials return JWT token
  - Invalid credentials return 401
  - Token expires after 24 hours
  - Rate limit: 10 requests per minute per IP

27.5.6 Specification View Content

Based on blueprint elements:

Blueprint Element Specification View Representation
Goal Functional objectives and success metrics
Capabilities Functional requirements and user stories
Interfaces API contracts, message formats, protocols
Workflows Behavioral sequences and state transitions
Success Metrics Acceptance criteria and performance targets
Constraints Non-functional requirements and limitations

27.5.7 Generation Method

  1. Extract Capabilities: Read capabilities: section from blueprint
  2. Extract Interface Contracts: Read interfaces: with protocols and formats
  3. Extract Workflows: Read workflows: for behavior description
  4. Extract Success Criteria: Read goal.success_metrics: and workflow completion criteria
  5. Extract Constraints: Read goal.constraints: and any additional constraints
  6. Format Output: Generate specification document (OpenAPI, requirements doc, etc.)

27.5.8 Specification View Checklist

When generating or reviewing specification views:

27.5.9 Common Pitfalls

❌ Including Implementation Details: Specifications define behavior, not how it’s implemented ❌ Vague Requirements: Specifications should be testable and unambiguous ❌ Missing Error Cases: Specifications must define behavior for error conditions ❌ Ignoring Edge Cases: Specifications should cover boundary conditions and unusual inputs

27.6 Operational View

27.6.1 Definition

The Operational View focuses on runtime behavior and operational processes. It answers “How does the system run and how do we operate it?”

27.6.2 Primary Audience

  • DevOps Engineers: Deploy and monitor systems
  • SREs: Ensure reliability and performance
  • Operations Teams: Handle incidents and maintenance
  • Support Teams: Troubleshoot production issues

27.6.3 What It Emphasizes

  • Workflows and execution sequences
  • Deployment procedures and environments
  • Monitoring and observability points
  • Operational procedures and runbooks
  • Performance characteristics and bottlenecks
  • Failure modes and recovery procedures

27.6.4 Typical Representations

  • Workflow Diagrams: Sequence diagrams, activity diagrams
  • Deployment Diagrams: Infrastructure and deployment topology
  • Operational Runbooks: Step-by-step procedures
  • Monitoring Dashboards: Metrics, alerts, and health indicators
  • Capacity Plans: Resource requirements and scaling strategies

27.6.5 Example Operational View

# Operational View: User Login Workflow

workflow: user_login

execution_sequence:
  1. User submits login credentials
  2. API Gateway receives request
  3. API Gateway validates input format
  4. API Service authenticates user
  5. API Service generates JWT token
  6. API Service caches session in Redis
  7. Response returned to user

monitoring_points:
  - name: login_request_count
    type: counter
    location: API Gateway
    labels: [endpoint, status_code]

  - name: login_duration
    type: histogram
    location: API Service
    buckets: [10ms, 50ms, 100ms, 500ms, 1s, 5s]

  - name: authentication_failures
    type: counter
    location: API Service
    labels: [failure_reason]

operational_procedures:
  - name: handle_high_failure_rate
    trigger: authentication_failures > 10/minute
    actions:
      - Check database connectivity
      - Verify Redis availability
      - Review authentication service logs
      - Escalate if persistent

  - name: handle_slow_logins
    trigger: login_duration p95 > 500ms
    actions:
      - Check database query performance
      - Verify Redis latency
      - Review system resource utilization
      - Scale services if needed

deployment_considerations:
  - API Gateway: Horizontal scaling, load balancing
  - API Service: Horizontal scaling, connection pooling
  - Redis: Cluster mode, persistence
  - Database: Read replicas for queries

27.6.6 Operational View Content

Based on blueprint elements:

Blueprint Element Operational View Representation
Workflows Execution sequences and operational procedures
Components Runtime instances and deployment units
Interfaces Runtime communication and monitoring points
Workflows (Error Handling) Failure modes and recovery procedures
Constraints Operational limitations and requirements
Workflows (Steps) Operational tasks and procedures

27.6.7 Generation Method

  1. Extract Workflows: Read workflows: section from blueprint
  2. Extract Error Handling: Read workflow error_handling: sections
  3. Identify Monitoring Points: Determine key metrics for each workflow step
  4. Define Procedures: Create operational procedures from workflows
  5. Identify Deployment Units: Map components to deployment artifacts
  6. Format Output: Generate operational documentation (runbooks, dashboards, etc.)

27.6.8 Operational View Checklist

When generating or reviewing operational views:

27.6.9 Common Pitfalls

❌ Including Architecture Details: Operational views focus on behavior, not structure ❌ Missing Error Handling: Operational views must cover failure scenarios ❌ Vague Procedures: Operational procedures should be specific and actionable ❌ Ignoring Monitoring: Operational views should define what to monitor and why

27.8.2 Generation Tools

27.8.2.1 1. Architecture View Generators

Input: Blueprint YAML (components, interfaces)

Output: Diagrams (Mermaid, PlantUML, Graphviz)

Example Tool:

def generate_architecture_diagram(blueprint):
    components = blueprint['components']
    interfaces = blueprint['interfaces']

    mermaid = "graph TD\n"

    # Add components
    for comp in components:
        external = "((External))" if comp.get('external') else ""
        mermaid += f"  {comp['id']}[{comp['name']}] {external}\n"

    # Add interfaces
    for iface in interfaces:
        connects = iface['connects']
        if len(connects) == 2:
            mermaid += f"  {connects[0]} -- {iface['protocol']} --> {connects[1]}\n"

    return mermaid

27.8.2.2 2. Specification View Generators

Input: Blueprint YAML (capabilities, interfaces, workflows, goal)

Output: OpenAPI spec, requirements document, test cases

Example Tool:

def generate_openapi_spec(blueprint):
    spec = {
        'openapi': '3.0.0',
        'info': {'title': blueprint['name'], 'version': blueprint['version']},
        'paths': {}
    }

    for iface in blueprint['interfaces']:
        if iface['protocol'] == 'HTTP/REST':
            # Generate endpoint definitions from interface
            # ...

    return spec

27.8.2.3 3. Operational View Generators

Input: Blueprint YAML (workflows, components, interfaces)

Output: Runbooks, monitoring configs, deployment manifests

Example Tool:

def generate_monitoring_config(blueprint):
    metrics = []

    for workflow in blueprint['workflows']:
        for step in workflow['steps']:
            metrics.append({
                'name': f"{workflow['id']}_{step['step']}_duration",
                'type': 'histogram',
                'labels': ['component', 'status']
            })

    return metrics

27.8.3 Manual Generation

When automated tools aren’t available:

  1. Extract Elements: Manually read relevant sections from blueprint
  2. Choose Format: Select appropriate representation (diagram, document, etc.)
  3. Structure Content: Organize according to projection type
  4. Validate: Cross-check against blueprint for consistency
  5. Version: Track projection version and blueprint version

27.9 Use Cases and Benefits

27.9.1 Use Case 1: Onboarding New Team Members

Challenge: New engineers need to understand system quickly

Solution: Provide appropriate projection for their role

  • Architects: Architecture view for structural understanding
  • Developers: Specification view for API contracts
  • Ops Engineers: Operational view for deployment and monitoring

Benefit: Faster onboarding, reduced learning curve

27.9.2 Use Case 2: System Integration

Challenge: Multiple teams need to integrate systems

Solution: Use specification views as integration contracts

  • Share API specifications from specification view
  • Reference interface definitions from architecture view
  • Understand data flow from operational view

Benefit: Clear integration contracts, reduced integration issues

27.9.3 Use Case 3: Incident Response

Challenge: Operators need to troubleshoot production issues

Solution: Use operational views for troubleshooting

  • Review workflow diagrams for execution paths
  • Check monitoring points from operational view
  • Follow error handling procedures from operational view

Benefit: Faster incident resolution, reduced downtime

27.9.4 Use Case 4: Architecture Review

Challenge: Team needs to evaluate architectural decisions

Solution: Use architecture view for structural analysis

  • Review component responsibilities
  • Analyze interface dependencies
  • Identify coupling and boundaries

Benefit: Better architectural decisions, reduced technical debt

27.9.5 Use Case 5: Compliance Auditing

Challenge: Auditors need to understand system controls

Solution: Use specialized projections (security, compliance)

  • Security view for authentication and authorization
  • Data view for privacy controls
  • Operational view for logging and monitoring

Benefit: Easier compliance, reduced audit preparation time

27.9.6 Overall Benefits

Benefit Description
Consistency All views derived from same blueprint, no drift
Efficiency Generate views automatically, reduce manual work
Traceability Trace any view element back to blueprint source
Maintainability Update blueprint, regenerate views automatically
Clarity Each view focused on relevant information
Collaboration Different teams get views tailored to their needs

27.11 Common Pitfalls and Best Practices

27.11.1 Pitfalls to Avoid

27.11.1.1 1. Creating Independent Documents

❌ Problem: Architecture diagram, API spec, and runbook created separately without linking to blueprint

✅ Solution: All projections are generated from blueprint and traceable back to source

27.11.1.2 2. Allowing Projections to Drift

❌ Problem: Projections updated manually without updating blueprint

✅ Solution: Update blueprint first, regenerate projections automatically

27.11.1.3 3. Over-Specifying in Projections

❌ Problem: Architecture view includes implementation details (class names, function calls)

✅ Solution: Keep projections at appropriate abstraction level

27.11.1.4 4. Wrong Projection for Audience

❌ Problem: Showing architecture view to QA team, specification view to ops team

✅ Solution: Match projection to audience and use case

27.11.1.5 5. Missing Projections

❌ Problem: System has blueprint but no projections generated

✅ Solution: Generate standard projections (architecture, spec, operational) for every blueprint

27.11.2 Best Practices

27.11.2.1 1. Always Start with Blueprint

✓ Design the blueprint first, then generate projections ✓ Don’t create projections without an underlying blueprint ✓ Treat blueprint as source of truth

27.11.2.2 2. Automate Projection Generation

✓ Build tools to generate projections from blueprint ✓ Integrate generation into CI/CD pipeline ✓ Version projections alongside blueprint

27.11.2.3 3. Keep Projections Current

✓ Regenerate projections when blueprint changes ✓ Store projection version with blueprint version ✓ Use automated validation to detect drift

27.11.2.4 4. Choose Right Projection for Audience

✓ Architecture view for architects and engineers ✓ Specification view for QA, product, and integrators ✓ Operational view for DevOps, SREs, and support ✓ Specialized views for specific needs (security, compliance, performance)

27.11.2.5 5. Maintain Traceability

✓ Link projection elements back to blueprint elements ✓ Document how projections are generated ✓ Track which blueprint version generated which projection

27.11.2.6 6. Validate Projections

✓ Test that projections accurately reflect blueprint ✓ Review projections with appropriate stakeholders ✓ Fix inconsistencies in blueprint, not projections

27.12 Advanced Topics

27.12.1 Specialized Projections

Beyond the three primary projections, specialized views can be generated for specific needs:

27.12.1.1 Security View

Focus: Security controls, authentication, authorization, data protection

Elements: - Data sensitivity classifications - Authentication and authorization mechanisms - Encryption requirements - Security monitoring points

27.12.1.2 Performance View

Focus: Performance characteristics, bottlenecks, capacity planning

Elements: - Performance targets from success metrics - Workflow duration estimates - Resource requirements - Scaling strategies

27.12.1.3 Compliance View

Focus: Regulatory compliance, audit trails, data governance

Elements: - Data retention policies - Audit logging requirements - Compliance controls - Regulatory mappings

27.12.1.4 Testing View

Focus: Test coverage, test cases, validation strategies

Elements: - Acceptance criteria from specifications - Workflow test scenarios - Error condition testing - Integration test points

27.12.2 Projection Composition

Multiple projections can be combined for comprehensive documentation:

Blueprint
    │
    ├─→ Architecture View
    │       └─→ Security Architecture View
    │       └─→ Performance Architecture View
    │
    ├─→ Specification View
    │       └─→ API Specification
    │       └─→ Test Specification
    │
    └─→ Operational View
            └─→ Monitoring Configuration
            └─→ Deployment Manifest

27.12.3 Projection Evolution

Projections evolve with the blueprint:

  1. Initial: Generate basic projections from v1.0 blueprint
  2. Refinement: Add details as blueprint matures
  3. Specialization: Create specialized views for specific needs
  4. Optimization: Improve projection generation tools and formats

27.13 Summary

The projection model presented in this appendix reinforces a key principle of the blueprint framework:

27.13.1 Key Principles

  1. Single Source of Truth: Blueprint is the primary representation
  2. Derived Views: All other artifacts are projections of blueprint
  3. Consistency: Projections remain aligned with blueprint
  4. Audience-Specific: Different projections serve different stakeholders
  5. Automatable: Projections can be generated automatically

27.13.2 The Three Primary Projections

Projection Focus Primary Audience Key Questions
Architecture View Structure Architects, Engineers How is it structured?
Specification View Behavior Product, QA, Integrators What should it do?
Operational View Runtime DevOps, SREs, Ops How does it run?

27.13.3 Benefits

  • Consistency: No drift between different artifacts
  • Efficiency: Generate views automatically
  • Clarity: Each view focused on relevant information
  • Traceability: Trace any element back to blueprint
  • Maintainability: Update once, regenerate all views

27.13.4 Action Items

For organizations adopting blueprint-based engineering:

  1. Establish Blueprint First: Always create blueprints before other documentation
  2. Build Generation Tools: Automate projection generation
  3. Integrate with Workflows: Make projection generation part of CI/CD
  4. Train Teams: Teach teams which projection to use for which purpose
  5. Maintain Discipline: Update blueprints, not projections

By treating architecture, specification, and operations as projections of a shared blueprint, the framework provides a consistent foundation for representing and evolving system knowledge.
