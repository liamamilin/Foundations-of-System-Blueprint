25  Appendix D — Example Blueprints (CLI / Web / Pipeline / Agent)

This appendix provides complete, detailed examples of blueprints created using the Blueprint Kernel v0.1.

The goal of these examples is to demonstrate how different system types can be described using the same structural framework. Each example includes:

  • Complete YAML structure following the template from Appendix A
  • Detailed structural descriptions explaining architecture decisions
  • Real-world context and use cases
  • Complexity notes and patterns
  • Cross-references to system types from Appendix B

These examples illustrate that diverse systems can be represented consistently using the shared blueprint model.

25.1 Example 1 — CLI Tool Blueprint

25.1.1 System Overview

The CLI Todo Manager is a command-line utility for personal task management. It provides simple yet effective task tracking capabilities accessible through terminal commands, making it ideal for developers and power users who prefer keyboard-driven workflows.

Use Cases: - Personal task tracking and reminders - Project-based task organization - Integration with shell scripts and automation - Quick task capture during development work

System Type: CLI Tool (Appendix B, Section 1) Complexity: small

25.1.2 YAML Structure

---
blueprint:
  id: cli.todo.manager.v1
  name: CLI Todo Manager
  version: 1.0.0
  system_type: CLI Tool
  complexity: small
  created_date: 2026-03-11
  authors: [Command Line Tools Team]

goal:
  description: |
    Provide a simple, efficient command-line interface for managing personal task lists.
    Enable users to create, organize, and track tasks with minimal friction.
  success_metrics:
    - metric: "Command execution time"
      target: "< 100ms (p95)"
      measurement: "Built-in timing"
    - metric: "User adoption"
      target: "50+ daily active users within 3 months"
      measurement: "Usage analytics"
  constraints:
    - type: usability
      description: "All commands must complete in under 1 second"
    - type: portability
      description: "Must run on Linux, macOS, and Windows"

capabilities:
  - id: capability.task_management
    description: Create, update, delete, and list tasks with metadata
    priority: critical

  - id: capability.project_organization
    description: Organize tasks into projects and categories
    priority: important

  - id: capability.task_search
    description: Search and filter tasks by various criteria
    priority: important

  - id: capability.data_export
    description: Export tasks to JSON, CSV, or Markdown formats
    priority: optional

components:
  - id: component.command_parser
    type: module
    responsibility: |
      Parse command-line arguments, validate input, and route commands
      to appropriate handlers. Supports subcommands and flags.
    technology: Rust with clap library
    complexity: small
    external: false

  - id: component.task_service
    type: module
    responsibility: |
      Manage task lifecycle including creation, updates, deletion, and queries.
      Enforce business rules and validation.
    technology: Rust
    complexity: small
    external: false

  - id: component.storage_layer
    type: module
    responsibility: |
      Persist task data to local filesystem with JSON-based storage.
      Handle file I/O, data serialization, and atomic writes.
    technology: Rust with serde for JSON
    complexity: small
    external: false

  - id: component.search_engine
    type: module
    responsibility: |
      Provide fast task search and filtering capabilities.
      Support multiple search criteria and patterns.
    technology: Rust
    complexity: small
    external: false

interfaces:
  - id: interface.cli_input
    protocol: Command Line Arguments
    connects: [user, component.command_parser]
    direction: input
    description: |
      Standard command-line input with subcommands and flags.
      Example: `todo add --priority high "Fix bug"`

  - id: interface.cli_output
    protocol: stdout/stderr
    connects: [component.command_parser, user]
    direction: output
    description: |
      Formatted output to terminal with colors and tables.
      Supports JSON output for programmatic use.

  - id: interface.storage_file
    protocol: File System (JSON)
    connects: [component.storage_layer, filesystem]
    direction: read_write
    description: |
      Local file storage in user's home directory.
      File: ~/.todo/tasks.json

  - id: interface.service_storage
    protocol: Internal Function Calls
    connects: [component.task_service, component.storage_layer]
    direction: request_response
    description: |
      Task service requests storage operations.

data:
  - id: data.task
    description: Individual task with metadata
    owner: component.task_service
    structure: |
      - task_id (UUID)
      - title
      - description (optional)
      - status (todo, in_progress, done)
      - priority (low, medium, high, urgent)
      - project (optional)
      - created_at
      - completed_at (nullable)
      - tags (list)
    sensitivity: internal
    retention: "Indefinite"

  - id: data.project
    description: Project for grouping related tasks
    owner: component.task_service
    structure: |
      - project_id (UUID)
      - name
      - description (optional)
      - color (hex code)
    sensitivity: internal
    retention: "Indefinite"

workflows:
  - id: workflow.create_task
    trigger: |
      User executes: `todo add [options] <title>`
    steps:
      - step: parse_command
        component: component.command_parser
        description: "Parse arguments and validate input"
        output: parsed_command

      - step: create_task_record
        component: component.task_service
        input: parsed_command
        description: "Create task with default values"
        output: task_record

      - step: persist_task
        component: component.storage_layer
        input: task_record
        description: "Save task to file atomically"
        output: persisted

      - step: display_confirmation
        component: component.command_parser
        input: task_record
        description: "Show created task to user"
        output: displayed
    completion_criteria: |
      Task created, persisted, and confirmation displayed
    error_handling:
      - condition: invalid_input
        action: display_error_and_exit
      - condition: storage_failure
        action: display_error_and_suggest_manual_recovery

  - id: workflow.list_tasks
    trigger: |
      User executes: `todo list [filter]`
    steps:
      - step: parse_command
        component: component.command_parser
        description: "Parse list command and filters"
        output: parsed_filters

      - step: load_tasks
        component: component.storage_layer
        description: "Load all tasks from storage"
        output: all_tasks

      - step: filter_tasks
        component: component.search_engine
        input: [all_tasks, parsed_filters]
        description: "Apply filters to task list"
        output: filtered_tasks

      - step: display_results
        component: component.command_parser
        input: filtered_tasks
        description: "Format and display task table"
        output: displayed
    completion_criteria: |
      Tasks loaded, filtered, and displayed
    error_handling:
      - condition: no_tasks_found
        action: display_empty_state_message
      - condition: storage_failure
        action: display_error_and_exit

  - id: workflow.complete_task
    trigger: |
      User executes: `todo done <task_id>`
    steps:
      - step: parse_command
        component: component.command_parser
        description: "Parse task ID"
        output: task_id

      - step: load_task
        component: component.storage_layer
        input: task_id
        description: "Load specific task"
        output: task_record

      - step: update_task_status
        component: component.task_service
        input: [task_record, "done"]
        description: "Mark task as completed"
        output: updated_task

      - step: persist_update
        component: component.storage_layer
        input: updated_task
        description: "Save updated task"
        output: persisted

      - step: display_confirmation
        component: component.command_parser
        input: updated_task
        description: "Show completion message"
        output: displayed
    completion_criteria: |
      Task marked as completed and persisted
    error_handling:
      - condition: task_not_found
        action: display_error_message
      - condition: already_completed
        action: display_info_message
---

25.1.3 Structural Description

The CLI Todo Manager demonstrates a straightforward, single-purpose system architecture suitable for command-line tools.

25.1.3.1 Component Interactions

  1. Command Parser serves as the entry point, handling all user input and routing
  2. Task Service contains business logic and enforces task rules
  3. Storage Layer abstracts file I/O and data persistence
  4. Search Engine provides filtering and search capabilities

The architecture follows a layered pattern with clear separation of concerns: - Input handling (Command Parser) - Business logic (Task Service) - Data access (Storage Layer) - Query logic (Search Engine)

25.1.3.2 Key Characteristics

  • Single Execution Context: Each command runs independently; no long-running process
  • State Persistence: State maintained via local file storage
  • Minimal Dependencies: No external services required
  • Composable Design: Can be used in shell pipelines via JSON output mode

25.1.3.3 Complexity Considerations

This is classified as a small CLI tool because: - 4 components with clear responsibilities - 4 interfaces (simple command-line I/O) - 2 data entities (tasks and projects) - 3 workflows (create, list, complete)

The blueprint could be expanded to medium complexity by adding: - Task dependencies and subtasks - Recurring tasks and reminders - Cloud sync capabilities - Plugin system for extensions

25.2 Example 2 — Web Application Blueprint

25.2.1 System Overview

The Blog Web Platform provides a complete solution for creating, managing, and publishing blog posts. It serves as a representative example of a typical web application with user authentication, content management, and public-facing content delivery.

Use Cases: - Authors create and publish blog posts with rich formatting - Readers browse and comment on posts - Administrators manage users and moderate content - Public RSS feed syndication

System Type: Web Application (Appendix B, Section 2) Complexity: medium

25.2.2 YAML Structure

---
blueprint:
  id: web.blog.platform.v1
  name: Blog Web Platform
  version: 1.0.0
  system_type: Web Application
  complexity: medium
  created_date: 2026-03-11
  authors: [Web Platform Team]

goal:
  description: |
    Provide a web platform for authors to create, manage, and publish blog posts,
    and for readers to discover and engage with content.
  success_metrics:
    - metric: "Page load time"
      target: "< 2s (p95)"
      measurement: "Real User Monitoring"
    - metric: "Concurrent users"
      target: "1000 concurrent users"
      measurement: "Load testing"
    - metric: "Content creation time"
      target: "< 5 minutes from login to publish"
      measurement: "User analytics"
  constraints:
    - type: performance
      description: "Support 10,000 page views per day"
    - type: compatibility
      description: "Support modern browsers (Chrome, Firefox, Safari, Edge)"
    - type: regulatory
      description: "Comply with accessibility guidelines (WCAG 2.1)"

capabilities:
  - id: capability.user_authentication
    description: User registration, login, and session management
    priority: critical

  - id: capability.content_creation
    description: Create, edit, and publish blog posts with rich formatting
    priority: critical

  - id: capability.content_display
    description: Display published posts to public readers
    priority: critical

  - id: capability.comment_system
    description: Allow readers to comment on posts
    priority: important

  - id: capability.content_search
    description: Search posts by keywords and tags
    priority: important

  - id: capability.rss_feed
    description: Provide RSS feed for syndication
    priority: optional

components:
  - id: component.web_frontend
    type: frontend
    responsibility: |
      Provide responsive web interface for content creation and consumption.
      Handle client-side routing and state management.
    technology: React + TypeScript
    complexity: medium
    external: false

  - id: component.api_service
    type: backend_service
    responsibility: |
      Expose REST API for frontend and serve public content.
      Handle authentication, authorization, and request processing.
    technology: Node.js + Express
    complexity: medium
    external: false

  - id: component.database
    type: data_store
    responsibility: |
      Persist users, posts, comments, and related data.
      Provide transactional data integrity.
    technology: PostgreSQL
    complexity: small
    external: false

  - id: component.cache_layer
    type: data_store
    responsibility: |
      Cache frequently accessed content and session data
      to improve performance and reduce database load.
    technology: Redis
    complexity: small
    external: false

  - id: component.search_index
    type: service
    responsibility: |
      Maintain search index for posts and enable fast search queries.
    technology: Elasticsearch
    complexity: small
    external: false

  - id: component.image_storage
    type: external_service
    responsibility: |
      Store and serve blog post images and media files.
    technology: AWS S3 or similar
    complexity: toy
    external: true

interfaces:
  - id: interface.http_api
    protocol: HTTP/REST
    connects: [component.web_frontend, component.api_service]
    direction: request_response
    description: |
      REST API for all frontend operations.
      Uses JSON request/response format.
    authentication: jwt_token

  - id: interface.database_connection
    protocol: PostgreSQL Wire Protocol
    connects: [component.api_service, component.database]
    direction: request_response
    description: |
      Direct database connection for data persistence.
      Uses connection pooling.
    connection_pool_size: 20

  - id: interface.cache_operations
    protocol: Redis Protocol
    connects: [component.api_service, component.cache_layer]
    direction: request_response
    description: |
      Cache access for session data and cached content.
    ttl_default: 3600

  - id: interface.search_api
    protocol: HTTP
    connects: [component.api_service, component.search_index]
    direction: request_response
    description: |
      Search queries for post content and metadata.

  - id: interface.image_upload
    protocol: HTTPS/REST
    connects: [component.api_service, component.image_storage]
    direction: request_response
    description: |
      Upload and retrieve images from cloud storage.

  - id: interface.public_content
    protocol: HTTP
    connects: [component.api_service, public_readers]
    direction: request_response
    description: |
      Public API for reading published posts (no auth required).

data:
  - id: data.user
    description: User account information
    owner: component.api_service
    structure: |
      - user_id (UUID, primary key)
      - email (unique, indexed)
      - password_hash (bcrypt)
      - display_name
      - role (author, admin)
      - created_at
      - updated_at
    sensitivity: confidential
    retention: "365 days after account closure"

  - id: data.post
    description: Blog post with content and metadata
    owner: component.api_service
    structure: |
      - post_id (UUID, primary key)
      - author_id (foreign key)
      - title
      - slug (URL-friendly identifier)
      - content (Markdown)
      - html_content (rendered HTML)
      - status (draft, published, archived)
      - published_at (nullable)
      - created_at
      - updated_at
    sensitivity: internal
    retention: "Indefinite"

  - id: data.comment
    description: User comments on posts
    owner: component.api_service
    structure: |
      - comment_id (UUID, primary key)
      - post_id (foreign key)
      - author_id (foreign key, nullable for anonymous)
      - content
      - status (pending, approved, rejected)
      - created_at
    sensitivity: internal
    retention: "Indefinite"

  - id: data.session
    description: User session tokens
    owner: component.api_service
    structure: |
      - session_id (UUID, primary key)
      - user_id (foreign key)
      - token_hash
      - expires_at
    sensitivity: confidential
    retention: "24 hours (automatic expiration)"

workflows:
  - id: workflow.user_login
    trigger: |
      User submits login form with email and password
    steps:
      - step: authenticate_user
        component: component.api_service
        description: "Verify credentials and generate JWT token"
        output: session_token

      - step: cache_session
        component: component.api_service
        input: session_token
        description: "Cache session in Redis"
        output: cached

      - step: return_response
        component: component.api_service
        input: session_token
        description: "Return token to frontend"
        output: login_response
    completion_criteria: |
      Valid credentials produce session token, invalid produce 401
    error_handling:
      - condition: invalid_credentials
        action: return_401_unauthorized
      - condition: database_error
        action: return_500_internal_server_error

  - id: workflow.create_post
    trigger: |
      Author submits new blog post
    steps:
      - step: authenticate_request
        component: component.api_service
        description: "Verify JWT token and extract user context"
        output: user_context

      - step: validate_content
        component: component.api_service
        input: user_context
        description: "Validate post title and content"
        output: validated_post

      - step: save_post
        component: component.api_service
        input: validated_post
        description: "Create post record in database"
        output: post_record

      - step: render_markdown
        component: component.api_service
        input: post_record
        description: "Convert Markdown to HTML"
        output: rendered_content

      - step: update_post
        component: component.api_service
        input: [post_record, rendered_content]
        description: "Save rendered HTML to post"
        output: updated_post

      - step: return_response
        component: component.api_service
        input: updated_post
        description: "Return created post to frontend"
        output: post_response
    completion_criteria: |
      Post created, rendered, and returned to author
    error_handling:
      - condition: unauthorized
        action: return_401_unauthorized
      - condition: invalid_content
        action: return_400_bad_request

  - id: workflow.publish_post
    trigger: |
      Author changes post status from draft to published
    steps:
      - step: authenticate_request
        component: component.api_service
        description: "Verify author authorization"
        output: user_context

      - step: update_post_status
        component: component.api_service
        input: [post_id, "published"]
        description: "Update post status and set published_at timestamp"
        output: updated_post

      - step: invalidate_cache
        component: component.api_service
        input: post_id
        description: "Clear cached versions of this post"
        output: cache_cleared

      - step: index_post
        component: component.api_service
        input: updated_post
        description: "Add post to search index"
        output: indexed

      - step: return_response
        component: component.api_service
        input: updated_post
        description: "Return published post"
        output: post_response
    completion_criteria: |
      Post published, cache invalidated, and indexed
    error_handling:
      - condition: not_author
        action: return_403_forbidden
      - condition: post_not_found
        action: return_404_not_found

  - id: workflow.view_post
    trigger: |
      Reader requests published post by URL slug
    steps:
      - step: check_cache
        component: component.api_service
        description: "Check if post is cached"
        output: cached_post

      - step: load_from_database
        component: component.api_service
        input: slug
        description: "If not cached, load from database"
        output: post_record

      - step: cache_post
        component: component.api_service
        input: post_record
        description: "Cache post for future requests"
        output: cached

      - step: return_response
        component: component.api_service
        input: post_record
        description: "Return post to reader"
        output: post_response
    completion_criteria: |
      Post returned from cache or database
    error_handling:
      - condition: post_not_found
        action: return_404_not_found
      - condition: post_not_published
        action: return_403_forbidden
---

25.2.3 Structural Description

The Blog Web Platform demonstrates a classic three-tier web application architecture with additional infrastructure components for performance and search.

25.2.3.1 Component Interactions

  1. Web Frontend: React-based SPA providing author and reader interfaces
  2. API Service: Node.js backend handling authentication, content management, and public content delivery
  3. Database: PostgreSQL for persistent storage of users, posts, and comments
  4. Cache Layer: Redis for session management and content caching
  5. Search Index: Elasticsearch for fast post search
  6. Image Storage: External cloud storage for media files

25.2.3.2 Key Patterns

  • Layered Architecture: Frontend → API → Database with caching and search layers
  • JWT Authentication: Stateless authentication with token-based sessions
  • Content Caching: Published posts cached to reduce database load
  • Search Integration: External search index for fast queries
  • External Service Integration: Cloud storage for images and media

25.2.3.3 Complexity Considerations

This is classified as a medium web application because: - 6 components including external dependencies - 6 interfaces with multiple protocols (HTTP, database, cache, search) - 4 data entities with relationships - 4 workflows covering critical operations (login, create, publish, view)

The architecture could be expanded to large complexity by adding: - Multi-tenant support for multiple blogs - Advanced content features (tags, categories, media galleries) - Real-time collaboration for co-authoring - Advanced analytics and user engagement tracking - CDN integration for global content delivery

25.3 Example 3 — Data Pipeline Blueprint

25.3.1 System Overview

The Analytics ETL Pipeline processes raw event data from various sources, transforms it into structured analytics data, and aggregates it for reporting. This example demonstrates a data processing system with multiple stages and batch processing workflows.

Use Cases: - Ingest user activity events from web and mobile applications - Transform raw events into structured analytics records - Aggregate data for dashboards and reports - Provide data warehouse access for business intelligence

System Type: Data Pipeline (Appendix B, Section 5) Complexity: medium

25.3.2 YAML Structure

---
blueprint:
  id: pipeline.analytics.etl.v1
  name: Analytics ETL Pipeline
  version: 1.0.0
  system_type: Data Pipeline
  complexity: medium
  created_date: 2026-03-11
  authors: [Data Engineering Team]

goal:
  description: |
    Ingest, transform, and aggregate user activity data for analytics reporting
    and business intelligence. Provide reliable, timely data for dashboards.
  success_metrics:
    - metric: "Data freshness"
      target: "< 4 hours from event to dashboard"
      measurement: "Pipeline monitoring"
    - metric: "Processing throughput"
      target: "1M events per hour"
      measurement: "Pipeline metrics"
    - metric: "Data accuracy"
      target: "> 99.9% valid records"
      measurement: "Quality checks"
  constraints:
    - type: reliability
      description: "Must handle duplicate events idempotently"
    - type: performance
      description: "Must process daily data within 6-hour window"
    - type: regulatory
      description: "Must comply with data retention and privacy policies"

capabilities:
  - id: capability.data_ingestion
    description: Ingest events from web, mobile, and API sources
    priority: critical

  - id: capability.data_transformation
    description: Clean, validate, and transform raw events
    priority: critical

  - id: capability.data_aggregation
    description: Aggregate transformed data for analytics queries
    priority: critical

  - id: capability.quality_monitoring
    description: Monitor data quality and detect anomalies
    priority: important

  - id: capability.data_lineage
    description: Track data origin and transformation history
    priority: important

components:
  - id: component.ingestion_service
    type: service
    responsibility: |
      Receive events from web/mobile clients and API sources.
      Buffer events and validate schema compliance.
    technology: Python + FastAPI
    complexity: medium
    external: false

  - id: component.message_queue
    type: infrastructure
    responsibility: |
      Buffer events between ingestion and processing stages.
      Provide reliable message delivery and replay capabilities.
    technology: Apache Kafka
    complexity: medium
    external: false

  - id: component.transformation_engine
    type: service
    responsibility: |
      Process events from message queue, clean and transform data,
      handle deduplication and enrichment.
    technology: Apache Spark
    complexity: medium
    external: false

  - id: component.quality_checker
    type: service
    responsibility: |
      Validate transformed data for quality and completeness.
      Detect anomalies and trigger alerts for issues.
    technology: Python + Great Expectations
    complexity: small
    external: false

  - id: component.data_warehouse
    type: data_store
    responsibility: |
      Store processed and aggregated data for analytics queries.
      Provide SQL access for BI tools and dashboards.
    technology: Snowflake
    complexity: medium
    external: false

  - id: component.metadata_store
    type: data_store
    responsibility: |
      Store pipeline metadata, data lineage, and quality metrics.
      Track pipeline runs and data versioning.

25.3.3 Structural Description

The Analytics ETL Pipeline demonstrates a multi-stage data processing system with batch and streaming components.

25.3.3.1 Component Interactions

  1. Ingestion Service: Receives events from clients and validates schema
  2. Message Queue: Kafka buffers events between ingestion and processing
  3. Transformation Engine: Spark processes, cleans, and transforms events
  4. Quality Checker: Validates data quality and detects anomalies
  5. Data Warehouse: Snowflake stores processed and aggregated data
  6. Metadata Store: PostgreSQL tracks pipeline metadata and lineage
  7. Alerting Service: Monitors health and sends alerts

25.3.3.2 Key Patterns

  • Event-Driven Architecture: Kafka enables decoupled event streaming
  • Batch Processing: Spark processes data in batches for efficiency
  • Quality Gates: Quality checker validates data before loading
  • Separation of Concerns: Ingestion, transformation, and aggregation are separate stages
  • Monitoring and Alerting: Continuous health monitoring with alerting

25.3.3.3 Complexity Considerations

This is classified as a medium data pipeline because: - 7 components including infrastructure services - 8 interfaces with multiple protocols (HTTP, Kafka, SQL, webhooks) - 4 data entities with different retention policies - 4 workflows covering ingestion, transformation, aggregation, and monitoring

The architecture could be expanded to large complexity by adding: - Real-time streaming with additional Kafka consumers - Machine learning model integration for anomaly detection - Multiple data sources with different schemas - Advanced data governance and privacy controls - Multi-region deployment for disaster recovery

The Autonomous Task Agent demonstrates an AI-powered system with planning, memory, and tool execution capabilities.

  1. Planner: Analyzes tasks and generates action plans using LLM

The architecture could be expanded to large complexity by adding: - Multi-agent coordination for parallel task execution - Hierarchical agent organization (master agent + specialist agents) - Advanced memory architectures with long-term learning - Tool marketplace with dynamic tool discovery - Human-in-the-loop workflows for approval and guidance
